# /document：產出目標專案的說明書

顧問流程產出的設計方案是**給設計者看的**。專案蓋出來要給別人用，還缺一份**說明書**。這個 skill 補這塊。

## 你在做什麼

把一個目標專案「給人看的文件」生出來。**兩種讀者要分開**，這對應設計面向 9 和 12 的分野：

- **給使用者的說明書**，放在目標專案的 `README.md` 和 `docs/`，用他的語言寫。
- **給維護者的文件**，放在目標專案的 `CONTRIBUTING.md`，給日後接手改的人。

**兩種語言各一版**，中英各一個檔，不要交錯排。

**對外公開的網站也是同一份事實拆成兩頁**，不是把兩種讀者塞進同一頁：

- `docs/index.html`（或等價的入口）是使用者版，語言深度比照使用者說明書。
- `docs/maintainer.html`（或等價）是維護者版，語言深度比照 CONTRIBUTING。

兩個入口頁互相連結，並明講「你現在看的是哪一版、另一版在這裡」。不要把兩種讀者塞進單一公開頁面。

## 開場檢查

1. 跑 `pwd` 確認在 `~/meta-harness`。產出用絕對路徑寫進目標專案，工作目錄不離開 meta-harness。
2. 確認目標專案的絕對路徑，沒給就問。
3. 讀 `docs/manual-template.md`，裡面有結構、雙語慣例、深度怎麼校準。
4. 不要重跑完整訪談。背景從既有的東西萃取。

## 第一步：先搞懂這個專案（動筆前必做，沒做完不准往下）

**不管有沒有現成的 README，都要先懂這個專案再動筆。**

讀的順序：

1. `CLAUDE.md`，看角色定義和核心規則。
2. `.claude/commands/` 的主要指令。**每一個指令都要讀完整內文**，包含模式、參數怎麼解析、開頭要問什麼、有哪些互動詢問。不是只看開頭那行描述。

   描述只講設計意圖。所有的叫法、以及互動行為（會用 `AskUserQuestion` 跳出來問什麼）都藏在內文裡。漏讀的話，你會把「一個指令有五種叫法」寫成「一種叫法」，也會漏掉「開頭一定會問視角」這種事。
3. `.claude/agents/*.md`，看各個 agent 負責什麼、要交出什麼。
4. `.env.example`，看存取和參數。
5. 設計方案。這是補充設計意圖用的，**不能取代**專案的現況。

讀完之後，用自己的話確認你答得出這三題：

- 這個工具是什麼？使用者拿它來做什麼？
- 使用者下什麼指令、會看到什麼、怎麼知道自己做對了？
- 它不做什麼？用錯了會怎樣？

說不清楚就是還沒懂，繼續讀。

現有的 README 不算「已經懂了」。那份可能是從設計者視角寫的，也可能早就過期。自我探索是去讀原始碼（指令和 agent 的定義），不是讀現有的說明書。

## 第二步：先講清楚讀者是誰（動筆前要輸出）

讀完專案之後，動筆前先明確輸出這份宣告：

```
使用者是誰：[誰]（例如：PM、RD、業務。工程方面是外行）
深度策略：
  - 業界術語（staging、dry-run、hook 這些）：[直接用 / 講白話展開]
  - 專案自己創的詞：第一次出現一定要白話註解，或直接改用功能名稱（不分內行外行）
  - 實作細節：[給 / 藏]
```

這份宣告決定了後面每一段要怎麼寫。沒輸出就動筆，等於跳過校準，要補做。

## 第三步：逐項對完段落清單再動筆

對照 `docs/manual-template.md` 裡給使用者的說明書結構，逐項確認：

| # | 段落 | 有專案裡的來源嗎 | 深度符合讀者嗎 | 備註 |
|---|------|--------------|-----------------|------|
| 1 | 這是什麼、能做什麼 | | | |
| 2 | 快速開始 | | | |
| 3 | 存取與參數 | | | |
| 4 | 怎麼用、常見任務 | | | |
| 5 | 工作流程迴圈：人和 AI 怎麼分工 | | | 專案有 AI 自動迴圈的話**必填**。畫出 AI 自動循環什麼、人什麼時候交出去、什麼時候拿回來驗收 |
| 6 | 有哪些指令和 skill | | | |
| 7 | 會產出什麼、怎麼確認做對了 | | | |
| 8 | 不做什麼、已知限制 | | | |
| 9 | 出錯怎麼辦 | | | |
| 10 | 誰維護、怎麼回報 | | | |
| 11 | 詞彙表（條件性）| | | |

每一段都必須有明確的來源：指令、agent、設定檔、`.env.example`。寫不出來源就標 `[需負責人補：X]`，不要用流暢的文字虛構。

## 內容從哪裡萃取

探索完之後對照這張表。設計方案是補充，不是主要來源。

| 要素 | 主要來源 | 補充來源 |
|---|---|---|
| 這是做什麼的、能做什麼 | `.claude/commands/` 的主要指令 | 設計方案 Part A |
| 使用者是不是這領域的內行 | 設計方案 Part A 裡「使用者懂不懂這個領域」那段，或 `docs/human-profile.md` | — |
| 安裝、存取、參數 | `.env.example`、`projects.yml` | 設計方案 Part A |
| 指令清單 | `.claude/commands/*`，逐一讀。**每個指令要列齊所有的叫法**，去讀內文裡講模式、參數解析、開頭步驟的那幾段，不要只抄開頭那行描述。**互動詢問**（會跳出來問什麼）要獨立一段呈現 | — |
| 產出和驗收方式 | `.claude/agents/*.md` 裡的交付物規格 | 設計方案 Part D 和 E |
| 已知限制、不做什麼 | 設計方案 Part A 和 F | CLAUDE.md 裡的禁止事項 |
| 架構和各元件怎麼串（維護者文件用）| `.claude/` 的目錄結構、hook、設定 | 設計方案 Part C 和 D |

現有的 README 不是萃取來源，它是要被合併的對象。讀它是為了保留人工手寫的部分，不是為了複製到新文件裡。

## 可以重跑，但不要盲目覆蓋

目標專案已經有 README 或 docs 的話，先判斷它是什麼性質：

- **純粹給使用者看的**（以「怎麼做」為導向）：合併刷新。偵測到大量人工手寫的痕跡，先問過再動。
- **混了設計者視角或架構細節**（hook 腳本名、設定路徑、agent 架構）：這**不算已經有使用者說明書**。要重構分流，把設計者才需要的細節移到 CONTRIBUTING，README 只留使用者視角。

重跑的時候要反映**當下已經驗證過**的專案狀態。列出來的指令和路徑，產出前先 grep 對一遍，避免文件講了但專案裡沒有。

## 雙語的產出規則

- 主檔用專案的工作語言。看目標專案既有的 README 和 CLAUDE.md 是什麼語言來判定，也可以用 `--primary zh|en` 覆寫。
- 主檔是中文：`README.md` 中文加 `README.en.md` 英文。主檔是英文就反過來，中文版用 `.zh-TW.md`。docs 和 CONTRIBUTING 同樣規則。
- 每個檔案第一行放語言切換，例如 `> 🌐 **繁體中文** | [English](README.en.md)`，依該檔的語言調整。
- **兩版在同一次、從同一份萃取出來的事實生成**，章節順序和錨點完全一致，這樣才不會慢慢走鐘。
- **不翻譯**：程式碼、路徑、指令、環境變數名、識別字、表格裡的值（顏色碼、px、node id）。只翻散文和表格標題。

## 寫檔和收尾

1. 逐個檔案用絕對路徑寫進目標專案：給使用者的說明書（README 兩版，加上必要的 docs 兩版），以及給維護者的文件（CONTRIBUTING 兩版）。
2. 收尾時跟對方說：產了哪些檔、主語言是什麼、哪些段落標了 `[需負責人補：X]`。
3. **寫完一定要跑獨立性自檢（R-12，這一關會擋下來）**：跑 `bin/r12-gate.sh <target>`。這是唯一的出處，不要手抄 grep 指令。

   退出碼 1 表示有命中，而且不是目標專案自己的文案，那就是洩漏。0 表示過關。2 表示用法錯或路徑不存在，那不是洩漏，先修參數。

   **先清乾淨，再跑一次 `bin/r12-gate.sh` 確認零命中，才能 commit。** 把它跑成「印出來看看」不算做過，那樣會帶著洩漏 push 出去。
4. 文件屬於目標專案的任務內容那一層。框架結構由顧問負責寫（R-9），要不要 commit 照那個專案自己的慣例。

## 常見的錯誤做法

| 錯誤做法 | 在講什麼 |
|---|---|
| 兩種讀者混成一份 | 給使用者的說明書塞進架構細節，或給維護者的文件用白話寫。這違反設計面向 9 和 12 的分流 |
| 對外只給單一版本 | GitHub Pages 或對外的首頁只生一個 index.html，把兩種讀者塞在一起。要拆成使用者版和維護者版兩頁，互相連結 |
| 一套模板套到底 | 不看使用者背景資料，內行和外行給同樣的深度 |
| 自創詞第一次出現沒註解 | 專案內部自己創的分類（像「內視 / 外視」「Stage X」「G-N / R-N」）不是業界術語。**不分內行外行，第一次出現一定要白話註解，或乾脆改用功能名稱**。內行可以直接用的只有業界通用的詞，像 staging、dry-run、hook 那些 |
| 指令只列一種叫法，或漏掉互動詢問 | 把「一個指令有五種叫法」寫成一種，或把「打完指令之後 AI 會跳出來問什麼」漏掉。結果使用者以為要記嚴格的語法，或不知道 AI 會跳出選擇題。逐個指令把叫法列齊；互動詢問要獨立一段呈現，寫清楚問什麼、選項有哪些、想跳過該帶哪個參數 |
| 雙語交錯排 | 中英同一段交錯，兩種語言都讀不順 |
| 流暢地虛構 | 寫出專案裡沒有的指令或參數，違反 R-4。該標 `[需負責人補：X]` |
| 把識別字也翻譯了 | 指令、路徑、環境變數名、顏色碼也翻譯，複製貼上就壞了 |
| 洩漏框架身分 | 目標專案的檔案引用 meta-harness、設計方案、規則編號、設計面向、顧問這類行話。目標專案要能獨立看懂，設計依據用它自己的話講（R-12）|
| 拿現有 README 代替探索 | 現有的 README 可能是設計者視角，也可能過期了。直接相信它等於沒懂專案就動筆。第一步一定要讀原始碼 |
| 只在後面加一段，不重構 | 現有 README 混了設計者才需要的細節，只在尾巴補幾段，使用者說明書還是不及格。應該重構分流，把那些細節移到 CONTRIBUTING |
