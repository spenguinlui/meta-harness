harness engineering · v0.4

不是 prompt engineering，
是整套系統的設計學。

meta-harness 是一位住在 Claude Code 裡的 AI agent 系統設計顧問。 腦中內建 13 大設計軸的 pattern library，陪你把任何 AI agent 工具（bash 腳本、web app、SaaS、hybrid 產品）設計好、蓋出來。

→ 在 GitHub 看 repo 怎麼開始 新手入口
01 · 這是什麼

它是顧問，不是腳手架。

你不會「執行」這個專案——你進到它的目錄、開一個 Claude Code session， 它就變成一位懂工法的建築師，陪你把某個 AI agent 工具（target repo）設計好。

它能幫你做三類事

你想做的事用哪個模式產出
新建 / 重新設計一個 AI agent 工具的骨架 /design 設計圖 + 直接寫進 target repo 的 wiring 檔案
健檢既有系統，用 13 軸找缺口、找反模式 /healthcheck 一份 13 軸對照健檢報告
回顧跑了一陣子的系統，看怎麼進化 /retro retrospective 紀要 + 行動建議
產交付說明書給他人使用 target repo /document 雙語 Viewer 說明書 + 維護者文件
為什麼是顧問而不是腳手架？ 因為 13 設計軸每一條都是設計參數而非開關，而且彼此耦合——沒有一組對誰都剛好的標準搭配。 所以採顧問模式：對話 + pattern library + 設計圖為主體，腳手架降級為顧問結論的編譯產物。
02 · 人類怎麼用

開一個 session，講白話。

沒有 framework、沒有 CLI、不用裝 dependency。 唯一硬需求是 Claude Code CLI 已安裝，以及——你心裡有一個想設計的 target repo（不需要已經存在）。

三行就開工

git clone <this-repo> ~/meta-harness
cd ~/meta-harness
claude        # 進去後 /model 切到最強，再打 /design ~/your-target

四個前門

/design

新建或重設一個 harness

走完整 6 步：訪談 → 設計圖 → review → 分期落地 → 自驗 → 驗收。

/healthcheck

定點體檢、找缺口

用 13 設計軸當鏡子掃描既有系統。冷啟動就能跑。

/retro

飛輪 retrospective

target 跑一陣子後回看：手做的動作該不該沉澱成 skill？

/document

產交付說明書

從 prescription + repo 現況自動萃取雙語說明書，不重新發明。

設計流程（/design 走完整 6 步）

步驟在做什麼誰主導
Step 1需求訪談（10–20 分鐘，5 件事）你 + 顧問（按鈕選擇題）
Step 2建築師獨自出設計圖顧問（你不用做事）
Step 3你 review，反覆收斂你給白話文字回饋
Step 4分期實作落地（Stage 1/2/3）顧問用絕對路徑寫進 target
Step 4.5自驗 loop（強制）：headless 跑 ≥ 3 次 + 機器評分顧問（不准肉眼瞄一眼 OK）
Step 5驗收（檔案存在、hook 觸發、權限對齊）顧問代跑 + 你跨 session 試用
Step 6飛輪 retrospective（數週後）你 + 顧問
Builder vs Human 的硬區分： Builder 是用 meta-harness 設計 target repo 的工程師；Human 是每天跑 target 指令的人（未必是該領域專家）。 設計軸 12「Human Interface」就是專門為 human 設計的翻譯層，對稱於設計軸 9「Observability」（給工程師看）。
03 · AI 運行邏輯

顧問身分 + 13 設計軸 pattern library。

顧問不是「萬能聊天機器人」。它載入時鎖定建築師人格：先聽清楚需求、先出設計圖、 再徵求 review、最後才動手寫檔。腦中有一份結構化 pattern library——這就是 13 設計軸。

13 大設計軸

每一條都是設計參數而非開關，彼此耦合——這正是為什麼要顧問而不要固定模板。

1Tool / Execution
2Context Management
3Memory
4Planning Loop
5Execution Loop
6Safety
7Hooks
8Evaluation
9Observability
10Multi-agent
11Triggers / Schedule
12Human Interface
13Self-verify Coverage

顧問的內建衛生規則（R-1 ~ R-12）

這些是 universal care rules——不管你設計什麼 target，顧問都必須遵守。由 .claude/hooks/ 強制執行：

  • R-1 / R-3 / R-5 / R-6 — cwd 守衛、行數檢查、提問自查
  • R-8 — 跨層越權禁止
  • R-9 — framework vs 任務內容分流
  • R-10 — 可機驗 outcome 必先自驗（Step 4.5 強制）
  • R-11 — 可被他人使用必交付雙語說明書
  • R-12 — grep 自檢明定為 blocking gate

顧問怎麼決策（Phase 0→1 重排）

不會一進門就動手。先 Phase 0 訪談確認 stakes，再進 Phase 1 設計。任何環節發現假設崩盤可重排回 Phase 0。詳見 docs/consultant-flow.md。

04 · 會產生哪些檔案 / 參數 / ENV

不需要 .env、不需要 API key。

這個專案本身不連任何外部服務、不存任何密鑰——它的「執行環境」就是 Claude Code 本身。 唯一的本機設定檔是targets.yml，純粹給你自己記錄 target 清單用，選用、不強制。

你需要準備的檔案

.env不需要不用 .env、不需任何 API key 檔。執行環境＝Claude Code 本身。

Session 過程中會產生的檔案

這些都是顧問在 session 裡幫你建立的「留痕」，全部已 gitignore（含真實 PII / 業主對話，不該上傳）：

路徑內容
sessions/<date>-<topic>.md每次需求訪談的紀要（5 段答案 + 設計軸篩選表）
prescriptions/<date>-<target>.md顧問動手前的設計圖 / audit trail
cases/特定 target 蒸餾出的案例
experiments/<target>-<topic>/runs/Step 4.5 自驗 loop 跑出的 raw 證據
BACKLOG.md你「踩到的規則 / 方法學缺口」未當場消化的清單

寫進「你 target repo」的檔案

Step 4 落地時，顧問用絕對路徑把 wiring 檔案直接寫進你的 target repo（cwd 不離開 meta-harness）。寫什麼由設計圖決定，常見的有：

.claude/hooks/*.sh                  # 自動執行的守衛 / 檢查
.claude/skills/<name>/SKILL.md      # 客製化技能
.claude/commands/*.md               # slash command 前門
.claude/settings.json               # hook 註冊 / 權限
環境變數？ 本 repo 自身不讀任何 env。 若你的 target repo 需要環境變數（例如要連 GCP、API），由顧問在 Step 1 訪談時問清楚並寫進 target 的設計圖——不汙染 meta-harness 本身。
