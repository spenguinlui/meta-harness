要改的是這套方法本身，
不只是你的工作區。

這頁給要擴充 meta-harness 本身的人：加一個新的設計面向、寫一條新規則、加一種模式或 skill、改設計方案和說明書的格式、補自我驗證的腳本。
只是想用這套流程設計你自己的工具？切到使用者版。

維護者該知道的事

六張卡片：架構長什麼樣、三個擴充入口、自我驗證怎麼擋關、有哪些原則不能破以及為什麼。

架構概覽
  • 角色層：.claude/skills/consultant/ 定義顧問角色和六步流程，document/ 產雙語說明書
  • 知識層：13 個設計面向、R-1 到 R-12、踩過的坑
  • 入口層：.claude/commands/ 的指令，加上 .claude/hooks/ 強制規則
  • 驗證層：experiments/meta-harness-eval/，即時數字看 coverage.json
  • 它不是 framework，是一個顧問角色、一份手法清單、一段對話流程
4 層 → 細節
加一個設計面向
  • 建 docs/design-axes/<編號>-<名稱>.md，寫清楚有哪些選項、跟別的面向怎麼牽連、常見錯誤做法、實際案例
  • 在 docs/design-axes.md 索引加一條
  • 把標題裡的總數加一，順手更新 healthcheck.md 裡的引用
  • 確認不跟現有的重疊。第 7 和第 11、第 9 和第 12 的界線已經劃清楚了，可參考
  • 跑 run-self-verify.sh 確認全過，總數對不上會被抓出來
5 步 擴充
加一條規則
  • 在 docs/universal-care-rules.md 加一個 ## R-N 段落
  • 判斷標準：換一個專案、換一個人，這條還成立嗎？跨得過去才收進通用規則
  • commit message 要回答「為什麼不能直接把問題的源頭砍掉」。這是 R-7：先找根本原因，不要疊規則掩蓋症狀
  • 還沒在別的專案上驗證過的，先寫進 docs/lessons.md 當心得，不要當強制規則
  • 自驗會跑 test-universal-care-rules-schema.sh，檢查編號是否連續
4 步，加上 R-7 的自問 → R-1~R-12
加一種模式或 skill
  • 建 .claude/skills/<名稱>/SKILL.md，frontmatter 的 name 和 description 必填
  • 在 consultant skill 的觸發表加一列
  • 需要的話掛進六步流程裡
  • 加一個 .claude/commands/<名稱>.md 當入口
  • 結構可以照抄 document skill
  • 驗證腳本用 test-skill-spec-format.sh，它會檢查 frontmatter 和引用有沒有對上
5 步 擴充
自我驗證怎麼擋關
  • 跑 bash experiments/meta-harness-eval/run-self-verify.sh，必須全過
  • 沒過的話 Stop hook 會擋住 session 結束，修好才放行
  • 驗證腳本涵蓋的範圍：交叉引用、設計方案格式、各專案的覆蓋率、設計面向文件、指令引用的數字一不一致、SKILL frontmatter、規則編號、Stop hook 行為、入口腳本完整性、指令流程、顧問用詞、coverage.json 格式
  • 寫新腳本時挑一種驗法：A 比對設定是否一致、B 觸發後看有沒有反應、C 跑分評輸出品質、D 比對前後差異
  • 自己驗自己是三層的：atdd-task 有自驗，是因為 meta-harness 規定自己也得自驗，而這條規定寫在 CONTRIBUTING 裡
即時數字見 coverage.json → 細節
四條不能破的原則
  • R-7：先找根本原因再修。疊規則掩蓋症狀，最後會變成一堆規則
  • R-8：自家層的問題在自家層修。方法層的規則不要寫進針對特定專案的文件
  • R-9：框架層歸框架層，任務內容歸任務內容
  • R-12：寫進目標專案的檔案要能獨立看懂。這條對 meta-harness 自己不適用，因為規則編號和設計面向就是這裡的共通語言
  • 為什麼是顧問不是產生器：13 個面向彼此牽連，沒有一組模板對所有人都剛好
  • 規則分層擺放：通用規則、流程、格式、常見錯誤做法各放各的地方
4 條原則加上設計理由 → 詳解
沒找到對應主題。換個關鍵字試試，或直接看原始碼。

動手前先過一遍這四件事

先 grep 找出根本原因（R-7）· 確認不跟現有的面向或規則重疊 · 要升成通用規則前，先在至少兩個專案上驗證過 · commit message 裡回答「為什麼不能把源頭砍掉」
