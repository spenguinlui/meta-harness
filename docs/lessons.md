# 踩過的坑

這裡記的是實際跑過 meta-harness 之後累積下來的教訓。

跟 `universal-care-rules.md` 的差別：那邊的 R-1 到 R-12 是已經變成強制執行的規則，這邊記的是設計決策背後的想法——為什麼要這樣設計、當初踩到了什麼。

---

## 設計方案會不自覺偏向 bash 和 Claude Code

那 13 個設計面向本身跟實作方式無關。工具執行、記憶、規劃、成效評估，對任何 AI agent harness 都成立，不管它是 bash 腳本、網頁應用、SaaS，還是混合型產品（像 OpenClaw、Hermes agent 這種本體是 SaaS 的 AI harness）。

偏差不在面向本身，在設計方案的 Part D。安裝清單預設寫的是 `.claude/hooks/`、`bin/`、`settings.json`，顧問看到這個格式就自然往 bash 套。結果對著一個需要 API route、資料庫結構、前端元件的專案，寫出完全不對的東西。

怎麼修：訪談「現在長什麼樣」那題一定要問實作介質——「這個工具最後跑起來是什麼樣子？CLI、網頁、API，還是嵌在某個產品裡？」設計方案的開頭要宣告實作介質，Part D 的內容跟著切換。

順帶界定一下適用範圍：目標專案裡面有 AI agent 就適用，不管用什麼做的。純軟體、完全沒有 AI 的，才超出範圍。

---

## 訪談那五題，每一題不問都有代價

那五個問題不是儀式，各自防一種具體的失敗。

- 沒問清楚想解決什麼問題，設計方案就會對著想像中的問題，不是實際的痛點。
- 跳過「不該做什麼」，設計方案就會自然膨脹。實作完之後要砍，比重寫還難。
- 沒問壽命，就預設是永久，於是不設計淘汰機制。結果一個一次性的工具堆了記憶和評估的全套，複雜度跟用途完全不成比例。
- 沒問使用者懂不懂這領域，就預設他是內行，於是不做翻譯層。結果對著一個外行人架起一面術語牆。

第一次用的人最容易跳過的是「不該做什麼」。顧問不逼的話，對方會說「都可以做」，然後三個月後設計方案膨脹到沒人認得出它。

---

## 寫進設定的東西比寫在 prompt 裡的持久

對話的上下文會被清掉，prompt 裡講過的建議下次 session 就不存在了。但 hook、settings.json、skill 在每次 session 開啟時都在。

一個 harness 設計得好不好，很大程度取決於：哪些約束是靠設定承載的，哪些只靠 prompt。只靠 prompt 的規則等於沒有規則。這不是設計者偷懶，是機制本身就不保證。

典型的失誤：把 R-6（不用沒解釋過的縮寫）只寫進 SKILL.md，顧問一旦自律失效就沒有第二道防線。後來補了一個 `pre-askquestion-reminder.sh` hook 來提醒。

---

## 13 個面向不是檢查表，是選項空間

第一直覺會是「13 條逐一填完，設計就完成了」。實際上它們是選項空間，多數專案只需要設計其中三到六條，剩下的用不到或一句帶過。

差別在哪：全部都填的話，設計方案會膨脹，對方 review 三十分鐘還沒有結論。先篩過的話，方案只剩下非做不可的那幾條，對方十五分鐘就能拍板。

篩選的依據來自訪談（壽命加上什麼時候會放棄），所以順序是訪談先做、設計方案後出，不能顛倒。

---

## 設計方案的價值在於「動手前強迫你想清楚」

`prescriptions/` 是被 gitignore 的過程文件。它的用處不是留存，是逼顧問在動目標專案之前先寫出「為什麼要這樣改、根據是哪個設計面向」。

寫不出方案就動手，等於是在還沒想清楚的時候實作。方案能很快寫完，代表設計已經清楚了；寫得磕磕絆絆，代表這一步還沒結束。

---

## 人的介面是最常被跳過的那個面向

設計者的預設假設通常是「每天用這工具的人跟我一樣懂這領域」。多數時候這是錯的，尤其是這幾種情況：

- 基礎設施工具給會計助理跑。
- 機器學習流程的輸出給業務 PM 看。
- 任何工具交接給下一個人。

翻譯層不是錦上添花，是基礎設施。跳過它，等於指令說明、輸出的語言、錯誤訊息都只有設計者自己看得懂。

從 ai-infra-management 第一版學到的實例：某個指令的說明用了內行才懂的術語（「4-stage architect-debate pipeline」），對方猜錯用法，這個指令對他來說形同關閉。改掉之後使用率直接回來了。

## 跨層越權是無意識的

meta-harness 的 README 原本有一張表：「大腦 model 用 Opus 4.7，手腳 model 用 Sonnet（目標專案用）」。

第一欄是講自家的情況，對的。第二欄是替另一層的人做決定，錯的。

寫的人沒意識到這是越權，覺得自己只是在「建議」。問題在於：建議寫進 README 就等於預設，預設就把另一層負責人的決策空間縮小了。

修正的方式是把第二欄改成「目標專案的負責人在他自己的 session 裡決定，meta-harness 不表態」。

檢查方法：看到「X 對，所以 Y 該……」這種對立句型，先停一下，想想那個 Y 是不是別人的決策範圍。

## 框架和任務內容要分開動

看到目標專案的 `CLAUDE.md` 行數違反 R-1（超過 50 行），顧問猶豫著不敢動，怕踩到 R-8 的跨層越權。

這是誤讀了 R-8。R-8 防的是替別人做業務決策。設定、檔案結構、規則紀律這些屬於框架，框架由顧問負責動。負責人在自己 session 裡寫的決策紀錄原文、操作手冊內容、業務邏輯才是任務內容，那才是他自己決定的範圍。

分辨方法：`.claude/` 裡的東西、`docs/` 裡的規則類文件、資料格式、指令定義，都是框架，顧問動。負責人拍板的決策內容、進行中的工作、執行時累積的資料，是任務內容，他自己動。

## 循環需要有人主動觸發才會轉

「計畫存成記憶」加上「成果累積成 skill」這個雙向循環，寫在設計方案裡看起來很美。但如果沒有明確定義「什麼時候要回來做回顧」，它就不會轉。

成效評估（8）和記憶（3）要一起設計，缺任何一個另一個就會退化：

- 沒有評估的記憶，就是垃圾一直累積，沒辦法淘汰掉沒用的。
- 沒有記憶的評估，每次都從零開始，沒有歷史可以參考。

所以設計方案的模板裡，記憶那段和評估那段要互相引用必填欄位，不然設計時很容易只做其中一個。

## 「驗證丟給對方」是預設會發生的失敗

顧問流程原本是：訪談、寫方案、實作、然後交給對方驗收。

實際發生的事：對方自己跑了三次，發現同一個 prompt 三次答案完全不同，而且流程在某些情境下會編造內容。這些問題，顧問交付前自己跑三次就會看到。

根本原因不是顧問懶，是流程沒有強制自驗。當「驗證」預設是交給對方做的時候，沒有任何機制阻止顧問把一個沒驗過的成品標上「通過」交出去。

2026-05-18 那次改造跑出來的自驗，抓到四個問題：

1. 評分誤判之一：「合併」這個詞有命中，但語境講的是 ElastiCache 節點，不是專案合併。
2. 評分誤判之二：「請你選一個視角」這種反問，被當成真的做了分析而通過。
3. 某條規則沒觸發：主 agent 把「使用者取消」當成了「對方明確叫停」。
4. 指令本身有個錯誤做法：看到 24 小時內有同類紀錄，就重播舊結論冒充成新的分析。

這四個問題，每一個都會以「通過」的姿態交付出去，然後由對方手動跑三次才發現。

修正的方式：R-10 強制機器驗得了的成果必須先自驗；第 4.5 步插在實作和驗收之間；設計方案的 Part E 加上驗證層級和自驗次數兩個欄位；用 `experiments/<目標專案>-<主題>/` 這個結構承載。

意外的收穫是：自驗流程本身也會踩到 R-10 自己的邊界情況（撞到 API 上限怎麼辦），把這些邊界情況寫進規則本身，規則就是自己用自己驗出來的。

## 診斷跟修補是兩回事

這套方法的原則是：任何失敗先找根本原因，不要疊症狀修補（R-7）。

實務上「疊修補」長這樣：失敗一次，加一條「這樣不行」。又失敗一次，再加一條。三個月後，一份文件裡有 12 條互不連貫的錯誤做法，而源頭的問題還在。

正確的做法：疊新規則之前先 grep 找根本原因，問自己「把源頭刪掉能解決嗎？」能的話就刪源頭，不要疊上去蓋住。

## 截圖比對的門檻不要用「整頁百分比」

做像素比對的視覺回歸測試，最直覺的通過線是「有差異的像素 ÷ 總像素 < X%」。這個門檻對局部小元件的位移完全失靈——而那正是最常見的跑版。改動只佔整頁極小的面積，被總尺寸一稀釋就掉到門檻以下了。

figma2code 的實例：分頁按鈕的間距放大了 3.2 倍（20px 變成 64px），但在 1440×2134 的整頁截圖裡只動了 130 個像素，也就是 0.004%，輕鬆溜過 0.1% 的門檻。回歸測試報「全綠」，是假通過。

關鍵的發現是：停掉所有動畫和轉場之後，同一頁重新截圖的雜訊底線是 0 像素——同一台機器、同一個瀏覽器，渲染是確定性的。既然沒改動就是 0 像素，門檻就該用絕對的像素數（例如超過 10 像素就算失敗），不是百分比。絕對門檻抓得到局部改動，又不會被整頁尺寸稀釋。

連帶學到兩件事。

截圖前一定要停動畫（注入 `animation-duration: 0` 和 `transition-duration: 0`），不然跑馬燈和輪播會讓比對結果永遠不穩，根本量不出雜訊底線。

百分比門檻其實是「跨機器要容忍反鋸齒差異」留下來的思維殘留。如果已經明確排除跨瀏覽器和 CI、只在本機跑，那就沒有反鋸齒的飄移，不需要用百分比去換容忍度，反而賠掉了靈敏度。

這條是自驗的直接產物：開一個全新的 agent，用自然語言的意圖去跑整套設定，agent 跑出「全綠」但不採信，深挖才現形。如果按照「丟給對方驗」的做法，對方會在改了元件、回歸報綠、以為安全的時候才踩到。

## 顧問會把自己的身分洩漏進目標專案

實作、寫目標專案文件的時候，顧問很自然會用自己的話寫設計依據：「因為 R-10」「對應設計軸 5」「完整設計圖在 prescription」。

但目標專案是獨立的，它的讀者手上沒有 meta-harness。這些就變成死連結，加上看不懂的框架行話。

根本原因是視角沒切換。顧問腦中，規則編號、設計面向、設計方案都是真實存在的東西，寫的時候忘了「對目標專案的讀者來說，這些不存在」。figma2code 那次拿自己試用之後，對方一眼就抓到五個檔案、七處洩漏。

修正的方式：設計依據要翻成目標專案語境下的白話——不是「因為 R-10」，而是「機器驗得了的改動，先自己跑過再交付」。設計方案、規則編號、設計面向都留在 meta-harness 本機。實作完之後 grep 自檢。

這跟 R-6（不用沒解釋過的術語）是同一個源頭，只是這次的術語是 meta-harness 自己的內部語言，最容易看不見。

**同一天學到的第二層教訓，代價更貴。** 立了 R-12 的 grep 自檢之後，顧問把它跑成了「印出來看看」，而不是「會擋住 commit 的關卡」。grep 明明命中了網站文件的洩漏，卻用 `||` 接著無條件 commit 加 push，洩漏就上了遠端，只能再補一個 commit 修掉。

教訓是：自檢只有當成會擋下來的關卡才有用。有命中就先清乾淨，再 grep 一次確認零命中，才能 commit。指令層面不要把檢查跟 commit 用 `&&` 串成一氣——檢查要先獨立跑、看結果，才決定要不要 commit。這條已經寫進 R-12 了。

## 說明書要畫出「AI 自動循環的流程和人機分工」，不只列任務

說明書模板給使用者看的那段，原本只有「我想做 X，就這樣說」，是一張任務清單。缺的是一段畫出「AI 會自動循環做什麼、人在哪裡交出去、什麼時候拿回控制」。

對那些會自己循環的專案——figma2code 的「寫程式碼、視覺檢查、再改」自動迴圈，ai-infra 的四位角色互相辯論的迴圈——這是它最大的特點，卻被淹沒在任務表裡。使用者看完不知道自己交出任務之後 AI 到底在自動做什麼、自己什麼時候該介入。

根本原因是：「常見任務」那一段回答的是「能叫它做什麼」，但沒回答「叫了之後控制流程怎麼跑」。這是兩個不同的問題。

對應到設計面向 5（執行迴圈）和面向 12（人的介面裡「什麼時候可以中斷、控制權何時交還」）。設計面向裡本來就有，但說明書模板漏了把它畫給使用者看。

修正：說明書模板加了給使用者的第五節「工作流程迴圈：人和 AI 怎麼分工」，會自動循環的專案必寫。用 ASCII 圖畫最清楚：誰在迴圈裡、AI 自動循環什麼、什麼時候回報等驗收。`/document` 的檢查清單也同步加上。

這是對方一句「很難理解到 AI 的工作流程迴圈」點出來的。

## 軟體工程的名詞不是學術裝飾，是設計階段的精度工具

harness 的設定設計常被當成「自由發揮的 prompt 加腳本」，但很多場景其實有現成的軟體工程做法可以對應：Strategy、Specification、Middleware、Facade、Repository、Bounded Context、Ubiquitous Language、Hexagonal、ATDD、單一職責加依賴反轉。

明講出採用了哪一種，設計討論的精度和 review 的效率都會提升。像是違反單一職責的肥大 hook、跨情境的共通語言逐漸走鐘，這些問題在設計階段就會被名字暴露出來，不必等到自我驗證才現形。

這不是為了套名詞而套。設定本來就在處理跟軟體工程相同的問題——可替換的引擎就是 Strategy，把規則變成資料就是 Specification，hook 串成一串就是 Chain of Responsibility——只是一直沒有被叫出名字。叫出來之後，review 的視角就從「這寫得對嗎」升級成「這個做法的取捨，在這個專案該怎麼選」。

LLM 領域特有的做法也是同理，那些傳統軟體工程沒有涵蓋的：四種自我驗證的驗法、agent 迴圈、prompt 快取的成本考量、model 路由、上下文視窗預算。一樣在設計階段就標出來，跨方案才能比對和重用。

對應 `prescription-template.md` 的軟工紀律映射段。寫設計方案時，顧問的判斷邏輯文件會提示用這套語言。

## 擋關的成本要對準風險，否則會對沒犯錯的人收稅

自我驗證用的那個 Stop hook，一開始設計成無條件全跑：每次收工都跑完整套驗證腳本才放行。直覺上「越嚴越好」，實際跑久了露出兩個問題。

一是純諮詢、純閱讀的 session，明明沒動任何檔案，照樣被罰跑一次。

二是更糟的歸因錯誤：某次純文件審查被擋下來，原因其實是前一輪遺留的問題，而且源頭在外部的 repo 沒修，但讀起來像是「你這輪做錯了」。

根本原因是：這道關卡的觸發條件，沒有跟它想防的風險對齊。R-10 要防的是「改了機器驗得了的東西卻沒驗就交付」，風險是由「有沒有改」構成的。無條件觸發等於把條件放寬成「有沒有收工」，多出來的部分全是稅。

修正的方式是加一道指紋判斷：比對架構檔的內容雜湊跟上次通過時的值，有改才驗，沒改就靜默放行。

有兩個關鍵不能省。第一，指紋只在通過之後才寫入，否則「改壞了不修，再收工一次」就會被指紋放行，這道關卡等於被自己繞過。第二，執行時產生的東西（log、報告、`runs/`）要排除在指紋之外，否則自己的輸出會觸發自己，變成永遠停不下來的空跑。

通則是：設計擋關機制的時候，觸發條件和阻擋條件要分開想。阻擋條件（發現對不上就 exit 2）通常一開始就設對了。被忽略的是觸發條件，而它決定了這道關卡會被當成防護還是被當成噪音。被當成噪音的，遲早會被人用 `--no-verify` 繞掉。
