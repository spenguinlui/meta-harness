# 設計面向 1：工具執行

模型輸出一個工具呼叫，harness 負責解析、執行、把結果回傳。看起來是最簡單的一條，實際上要決定的細節最瑣碎。

## 要決定的事

### 一、顆粒度

**做細一點**，一個工具只做一件事，讓模型自己組合。彈性好、可組合，但模型要來回好幾輪才能完成複雜任務。

**做粗一點**，一個工具就跑完整個工作流。快、便宜，但失去細部控制。

**折衷**是把常用的組合包成粗的，邊界情況留細的。

判斷標準：這幾個動作是不是總是一起做，而且失敗時可以整體退回？是的話包在一起，不是的話拆開。

### 二、宣告副作用

每個工具都要標清楚它會不會改動東西：

- 唯讀：純查詢。
- 會改動：改了狀態，但可以復原。
- 有破壞性：改了狀態，而且不可逆。

harness 依據這個標記套用不同的安全策略，例如有破壞性的一律強制確認。

### 三、重複執行結果會不會一樣

一樣的話，失敗了可以放心重試。不一樣的話，重試之前要先檢查是不是已經執行過了，通常靠一個識別鍵來判斷。

會產生不同結果的工具必須明確標記，不然自動重試會出事。

### 四、輸入格式

哪些欄位必填、哪些選填，型別和範圍是什麼，附上範例值給模型參考。

還有預設值：危險的操作預設要保守，例如 `dry_run=true`。

### 五、輸出格式

成功時是什麼結構，失敗時是什麼結構（錯誤碼、訊息、能不能重試）。

還有部分成功怎麼辦：批次操作裡五件成功了三件，要怎麼回報。

輸出格式不穩定的話，成效評估寫不出來，快取的命中率也會低。

### 六、同步還是丟到背景

短任務同步跑就好。長任務丟到背景，之後再查狀態。

要決定的是：超過幾秒該丟背景？harness 要不要主動去輪詢狀態？

### 七、失敗的時候 harness 該做什麼

直接把錯誤回灌給模型？自動重試 N 次？還是升級成「停下來問人」？

這一條跟執行迴圈的牽連最深。

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 上下文管理 | 工具的輸出會進上下文。格式不穩定，快取就失效 |
| 記憶 | 有破壞性的工具該觸發寫入記憶，留下決策紀錄 |
| 規劃 | 副作用的宣告決定了規劃要多嚴格 |
| 執行迴圈 | 失敗策略決定迴圈怎麼往前走 |
| 權限與安全 | 破壞性的標記就是安全策略的依據 |
| 成效評估 | 輸出格式是每步驗證的基礎 |

## 常見的錯誤做法

**一個工具又能讀又能寫。** 同一個工具負責查也負責改，副作用的宣告就模糊了。像 `update_user(id, fetch=True)` 這種靠參數切換的，拆成兩個。

**什麼都用字串。** 所有參數都是字串、輸出都是自由文字。模型每次都要重新解析，成效評估也寫不出來。應該強制用 JSON 或其他結構化的輸出。

**用特殊值偷懶。** 用 `-1` 表示「沒有」、用空字串表示「用預設值」。模型很容易誤用。改用 `null` 或明確的列舉值。

**名稱跟行為不符。** `get_user_info` 看起來只是查詢，結果它還會更新 last_login。藏起來的副作用會讓 harness 的安全策略整個失效。

**一個工具做 20 件事。** 靠參數切換完全不同的行為。模型選錯參數就會跑錯動作。拆開比較安全。

**沒有範例值。** 格式定義只寫「string，使用者 ID」，模型只能瞎猜格式。給範例值是最便宜的 prompt 工程。

**用解析器來回轉換人寫的結構化檔案。** `json.load` 之後 `json.dump`，會把原本寫成一行的陣列展成很多行，產生上千行的噪音 diff。`jq` 重排 key、`yq` 改縮排也是同一類問題。

對人寫的 JSON 或 YAML 要做最小修改，用逐行編輯的方式（sed 或編輯工具）。解析器不保證保留原本的排版。
