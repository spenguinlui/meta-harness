# 設計面向 9：可觀測性

成效評估給的是分數，也就是「做得對不對」。可觀測性給的是原因：為什麼這樣做、花了多少、卡在哪裡。兩者是一對。

## 該觀測什麼

**執行軌跡。** 每一次工具呼叫的時間、參數、回傳、耗時；每一個 hook 的觸發；規劃和重新規劃的事件；評估的觸發和結果。

**成本。** token 用量（輸入、輸出、快取命中的）、快取命中率、每個任務花多少錢、每個 skill 或每個操作花多少錢。

**效能。** 每個任務的實際耗時、工具延遲的分布、卡在哪一步最久、實際達到的並行程度。

**失敗。** 失敗率，要按類別分：工具失敗、評估失敗、使用者中斷。還有哪個工具最常失敗、哪類任務最常需要重新規劃、使用者中斷的比例。

**行為。** 平均步數、重複呼叫的比例（這是在原地繞圈的跡象）、計畫的採用率（做了計畫之後真的照著跑嗎）、記憶的寫入頻率和召回率。

## 要決定的事

### 一、記多細

太細的話 log 會爆炸、處理變慢。太粗的話出事查不到。

通常工具呼叫這一層一定要記，模型 token 那一層可選。

### 二、要不要抽樣

正式環境流量大就要抽樣。特定領域的 harness 通常規模小，可以全記。

失敗的案例一律全部留下。

### 三、存在哪

- 本機檔案：簡單，但很難做跨 session 的分析。
- 結構化的 JSONL：可以查詢。
- 追蹤平台（Langfuse、Helicone 這類）：可以視覺化、可以比較。
- 自己管的資料庫。

### 四、隱私

追蹤紀錄裡包含對話內容和工具參數，可能含有密碼或個資。要先過濾再存。

### 五、即時看還是事後看

開發中需要即時的儀表板。跑完一批之後需要的是事後分析。

這兩種需求不同，用的工具也不同。

### 六、跟評估和記憶怎麼接

失敗的追蹤紀錄要自動變成評測集的候選。高頻出現的成功模式要自動進記憶。

沒有這些接口，追蹤紀錄就只是垃圾。

### 七、觀測本身的成本

寫 log 是有開銷的。同步寫會拖慢執行。比較重的觀測該丟到背景。

### 八、可比性

不同版本 harness 的追蹤紀錄要能互相比較，所以格式要穩定、欄位要一致。

不然「第二版比第一版好」這句話說不清楚。

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 成效評估 | 觀測提供原因，評估提供分數，必須一起看 |
| 記憶 | 失敗的追蹤紀錄進記憶；追蹤的統計數字驗證記憶還有沒有用 |
| Hook | 觀測常常用 hook 來實作，在工具前後寫 log |
| 執行迴圈 | 預算的監控靠觀測 |
| 工具執行 | 工具該標上成本和延遲的屬性 |
| 權限與安全 | 稽核 log 是安全和觀測重疊的地方 |

## 常見的錯誤做法

**只記不看。** log 量很大但沒人分析，出事還是查不到。至少要能查詢、要有摘要。

**沒記成本。** 跑了一個月才發現帳單爆掉。至少要記到 token 和金額，能分到任務、使用者、skill 這幾層更好。

**失敗不分類。** 全部記成「failed」一坨，不分是工具失敗、評估失敗，還是使用者中斷。這樣改進無從下手。

**追蹤的格式不穩定。** 每一版都加欄位、改型別，跨版本的比較就失效了。加欄位沒問題，但改既有欄位要做遷移。

**觀測拖慢執行。** 每一步都同步寫追蹤紀錄到遠端，使用體驗會崩。丟背景。

**隱私外洩。** API key 進了追蹤紀錄、進了 log 平台。過濾要在寫入端做，不是事後再刪。

**觀測沒接評估和記憶。** 追蹤紀錄自成孤島，失敗的案例沒有回流到評測集，成功的模式也沒進記憶。

**沒有基準線。** 「這次跑了 30 秒」，這是快還是慢？沒有歷史數據可以對比。至少留下中位數和 95 百分位。

**儀表板沒人看。** 建得很漂亮，但沒有進到維運流程裡。該定期 review，該設告警。

**主入口用 `exec` 收尾，跟觀測互斥。**

如果 harness 的入口是用 `exec "$action_script" "$@"` 結尾的（好處是行程樹乾淨、退出碼會自動傳遞），那麼所有事後的 hook——稽核、指標、異常偵測——都不可能跑到，因為 `exec` 已經把行程換掉了。

要支援觀測就必須改成 fork、wait、然後回填退出碼。

這是可信度背後隱藏的行程模型成本。規劃稽核和觀測時，要把這個取捨講明白。
