# 設計面向 5：執行迴圈

模型和工具一來一往的那個迴圈引擎。它是承載其他所有流程運轉的底層心跳。

注意這跟「規劃、執行、評估」裡的那個「執行」不是同一件事。那個是單一步動作，這個是整個迴圈。

## 要決定的事

### 一、什麼時候停

可能的條件：模型自己宣告完成、達到步數上限、偵測到反覆做同樣的工具呼叫、連續 N 步都沒有實質進展、token 超出預算、時間超出預算、成本超出預算、評估連續失敗。

多個條件要排出優先順序。

### 二、給多少預算

- 步數：最多幾次工具呼叫。
- token：上下文的 token 上限。
- 成本：花費的上限。
- 時間：實際經過時間的上限。

少設一個，就有可能跑到天荒地老。

### 三、並行還是照順序

哪些工具呼叫可以並行（唯讀的通常可以）？哪些必須照順序（有相依、有副作用）？並行時有一個失敗怎麼辦（其他繼續還是全停）？同時最多跑幾個？

### 四、出錯怎麼辦

從輕到重的處理策略：

- **原樣重試**：同樣的呼叫再試一次，適合暫時性的錯誤。
- **等一下再重試**：退避一段時間再試。
- **改寫再試**：讓模型自己改寫這次呼叫。
- **回頭重新規劃**。
- **停下來問人**。
- **整個任務中止**。

哪一類錯誤對應哪個策略，要事先設計好，不是當下憑感覺決定。

### 五、中斷和恢復

對方可不可以中途插話改方向？當機或斷線之後能不能接著跑？背景任務怎麼掛回主迴圈？做到一半的狀態怎麼存？

長任務沒有恢復機制，一斷就要全部重來。

### 六、什麼時候把控制權交還

做有破壞性的動作之前、指令模糊、超出預算、有好幾個合理的選項、高風險的決定。

太自動會失控，太常問人就沒有自動化的價值了。

### 七、怎麼判斷「沒進展」

同樣的工具呼叫重複出現（參數完全一樣）、工具呼叫不同但上下文沒有變化、模型的輸出在原地打轉。

要判斷這件事，需要某種「狀態指紋」來比對。

### 八、非同步任務

短任務同步跑就好。長任務丟到背景。要決定的是：背景任務的結果怎麼通知回主迴圈？同時有多個背景任務怎麼管理？

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 規劃 | 計畫的步數就是迴圈的步數預算 |
| 成效評估 | 每步驗證失敗會觸發重試或重新規劃 |
| 記憶 | 任務完成後寫記憶，是迴圈結束之後的事件 |
| 工具執行 | 工具的失敗策略決定了迴圈的行為 |
| 權限與安全 | 交還控制權就是安全機制的切入點 |
| 可觀測性 | 每一步都要記錄，不然出事查不到 |

## 常見的錯誤做法

**沒設預算。** 信任模型自己會停，結果卡在迴圈裡跑到沒錢。至少要有步數和成本兩道保險。

**失敗就一直重試。** 遇到 5xx 就無限重試，不分錯誤類型一律重試。應該要分：暫時性的可以重試，永久性的就停下來。

**偵測不到迴圈。** 模型反覆做同樣的檢查，harness 沒有擋。至少要抓「同一個工具加上同樣的參數，連續 N 次」。

**不支援中斷。** 對方看出方向錯了卻沒辦法插話，只能 Ctrl+C 整個重來。主流的 harness 都有中斷機制，Claude Code 用的是 ESC。

**背景任務變黑洞。** 丟出去之後就忘了，沒辦法查進度、也不會通知結果。至少要能列出來、查狀態、看輸出。

**太自動。** 有破壞性的動作也不停下來，一錯就是大錯。安全機制和執行迴圈必須協作。

**太常問人。** 每個工具呼叫都要確認，對方會疲乏，自動化就失效了。要做信任分級。

**不能接著跑。** 一個 30 分鐘的任務跑到第 25 分鐘斷線，全部重來。至少計畫和已完成的步驟要持久化。
