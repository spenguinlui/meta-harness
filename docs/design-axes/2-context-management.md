# 設計面向 2：上下文管理

單一 session 裡，token 額度怎麼分配。

上下文是模型「當下看得到的一切」，它不是無限的。

## 要決定的事

### 一、哪些東西自動載入

什麼該進系統 prompt？通常是專案規則（CLAUDE.md、AGENTS.md）、重要的狀態檔（清單、註冊表）、工具的能力描述。

判斷標準：每次任務都會用到，而且夠穩定、不會把 token 撐爆。不符合的話改成用到才載。

### 二、哪些用到才載

由模型主動去讀的部分：大檔案（程式碼、log、資料）、很少用到的工具的詳細格式、歷史紀錄。

工具搜尋、漸進式揭露，都是這一層的設計。不要把 100 個工具全塞進系統 prompt，先搜出相關的再給。

### 三、超過上限怎麼壓縮

- **截斷**：把最舊的丟掉。粗暴但簡單。
- **摘要**：讓模型自己壓縮歷史，Claude Code 的自動壓縮就是這種。
- **滾動視窗**：保留最近的 N 筆，加上最關鍵的 M 筆。
- **分支**：開一個 sub-agent 把它隔開。

### 四、快取

Anthropic 的 prompt 快取存活 5 分鐘。要決定的是：

哪些段落穩定到值得快取（系統 prompt、規則、工具定義）？哪些變動很快、不該被快取干擾（最新狀態）？快取的分界點放在哪裡？

快取命中率是成本和速度上最大的槓桿。

### 五、用 sub-agent 隔離

複雜的任務丟給 sub-agent 跑，主上下文只看摘要。

探索性的任務（grep、搜尋）適合外包出去，主對話可以保持乾淨。但 sub-agent 的結果會比較淺，不適合需要全局判斷的工作。

### 六、順序要穩定

快取對順序很敏感。穩定的段落放前面，會變動的放後面。順序一亂，快取就不會命中。

### 七、資訊密度

上下文不只是 token 數量的問題，還有資訊密度。

同樣 1000 個 token，一坨原始 log 跟一份結構化的摘要，價值差很多。要給模型「對它有用」的部分，不是「全部的資訊」。

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 工具執行 | 工具的輸出會進上下文，輸出大小決定了壓力有多大 |
| 記憶 | 記憶召回之後要塞進上下文，召回策略會吃掉額度 |
| 執行迴圈 | 步數越多上下文越長，迴圈的終止條件要看 token 用量 |
| 規劃 | 計畫本身該定義「這個任務需要哪些上下文」 |
| 成效評估 | 跑評估時要重置上下文，不然會互相污染 |

## 常見的錯誤做法

**全部塞進系統 prompt。** 把所有可能用到的東西都塞進去。看起來快取有命中，實際上每次都在讀整本書。應該改成漸進式揭露。

**把會變的東西放前面。** 例如把「當前時間」放在系統 prompt 開頭，快取永遠不會命中。會變動的一律放後面。

**把冗長的 log 整段塞回去。** 跑一次 build 產生 100 行 log 全進上下文。應該截掉尾巴、抓出錯誤、做成摘要。

**濫用 sub-agent。** 什麼事都開一個 sub-agent，主對話反而失去細節判斷的能力。sub-agent 適合的是邊界明確的子任務。

**不分層。** 記憶、上下文、工具參數全混在一起，模型分不清哪些是規則、哪些是現況、哪些是這次任務的參數。應該切成明確的區塊，用 XML 標籤或 markdown 標題分開。

**破壞快取。** 動態的時間戳、隨機的 ID 出現在穩定區，整個快取就失效了。動態的值集中放在尾段。
