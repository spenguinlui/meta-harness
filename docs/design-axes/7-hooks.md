# 設計面向 7：Hook

在工具呼叫的前後、session 的邊界、以及特定事件發生時，插入自訂的行為。

hook 是「靠 harness 自律」和「由平台強制」兩者的分野。

## 有哪些 hook

**工具的前後。** 工具執行前可以擋下來、可以改參數、可以注入額外的上下文。工具執行後可以驗證、記錄、把訊息回灌給模型。

**session 的邊界。** session 開始時載入專案規則和提醒事項；session 結束時清理，並把摘要寫進記憶；上下文壓縮時也可以介入。

**跟人互動的時候。** 對方輸入之後、模型開始處理之前；以及系統要通知對方的時候。

**檔案和 Git。** commit 之前跑 lint；寫檔之前做驗證。

每家 harness 提供的 hook 位置不一樣，Claude Code 有完整的一套。

## 要決定的事

### 一、強制還是建議

強制的話，hook 失敗就擋下來，工具不能執行。建議的話，失敗只發警告，流程繼續。

跟安全有關的用強制，跟風格和品質有關的用建議。

### 二、hook 自己壞掉怎麼辦

腳本寫錯、執行超時，這時候要：

- 當作 hook 沒跑，繼續往下（失敗時放行）。
- 擋住整個流程（失敗時擋下）。

風險高的用失敗時擋下。

### 三、效能預算

hook 每次都會跑，所以要快。

同步的 hook 不該超過幾百毫秒。慢的部分丟到背景去，發出去就不管。不然使用體驗會崩掉。

### 四、副作用要看得見

hook 改了什麼，要讓人和模型都知道。

默默改掉參數會讓除錯變得非常困難。有變更就該記錄下來。

### 五、順序和組合

同一個事件掛了多個 hook 時，順序怎麼定？要明確排序。

任何一個失敗就中止，還是全部跑完？衝突的時候誰贏？

### 六、設定的層級

全域（使用者層）、專案（repo 層）、個人覆寫。要決定哪一層優先。

### 七、可觀測性

要知道 hook 有沒有被觸發、跑了多久、有沒有擋下什麼東西。

沒有觀測的 hook 會默默壞掉，而且沒人發現。

## hook 是其他面向的實作機制

很多面向要做的事，最後都是靠 hook 來實現：

| 那個面向要做的事 | 用 hook 怎麼做 |
|---|---|
| 安全：破壞性操作強制確認 | 工具執行前攔截，要求在對話裡確認 |
| 成效評估：每個動作後驗證 | 工具執行後跑驗證腳本 |
| 記憶：自動寫決策紀錄 | 操作完成後觸發寫入 |
| 可觀測性：留下追蹤紀錄 | 工具前後寫 log |
| 上下文：載入規則 | session 開始時注入 |

沒有 hook 機制的話，這些事只能靠 prompt 引導，那是很弱的保證。有 hook 就是平台強制，保證強得多。

## 常見的錯誤做法

**全部用 prompt，不用 hook。** 在 CLAUDE.md 寫「請每次 commit 前跑 lint」，模型偶爾就會跳過。該強制的就用 hook，不要當成建議。

**hook 掛太多。** 每個工具都掛五個 hook，累積的延遲會爆炸。只在關鍵的地方掛。

**慢的 hook 同步跑。** 工具執行前跑一個 30 秒的 lint，對方會以為 harness 當掉了。慢的動作丟背景。

**安全用的 hook 設成失敗時放行。** 安全檢查的 hook 自己壞了就等於通過，那跟沒檢查一樣。跟安全有關的一律設成失敗時擋下。

**hook 改了參數卻不記錄。** 模型以為自己呼叫了 X，實際上被改成 Y。行為跟認知分家，除錯會是噩夢。

**hook 沒有可觀測性。** 沒人知道它有沒有跑，也沒人知道為什麼被擋。至少要有 log。

**把業務邏輯塞進 hook。** 把核心功能寫在 hook 裡，hook 一失敗功能就消失了。hook 是邊界，不是主體。

**個人偏好寫成專案的 hook。** 那是在強迫整個團隊接受你的風格。該寫在使用者層，不要寫在 repo 層。
