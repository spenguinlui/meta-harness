# 設計面向 10：多 agent 協作

把任務拆給多個 agent，並行或串聯處理，由主 agent 負責調度。

業界的趨勢是從「一個 agent 自己跑一個很長的對話迴圈」，轉向「多個各司其職的 agent，透過明確的交接方式協作」。可以參考 2026 年關於 LLM agent 外部化、以及多 agent 流程工程的討論。

2026 年 7 月，這一層被業界稱為 graph engineering，也就是「圖的工程」。它是迴圈工程的下一層：迴圈讓單一 agent 的行為可以程式化，圖讓多個 agent 的組織方式可以程式化。這一波討論的核心概念——驗證節點、有預算的回邊、長期編制對上單次任務的結構、調度邏輯放哪——對應到下面的第五、九、十項。

---

## 為什麼它是獨立的一條，不併進執行迴圈

執行迴圈（面向 5）講的是單一 agent 內部「模型跟工具」的迴圈。

多 agent 協作講的是多個 agent 之間怎麼交接、各自看得到什麼上下文、結果怎麼整合。

兩者要決定的事完全不同：並行失敗的策略、上下文要隔離到什麼程度、子 agent 該拆多細。2026 年之後業界普遍把多 agent 當成獨立的架構層。

## 要決定的事

### 一、什麼時候才開 sub-agent

- **上下文快爆了**：主對話的 token 用量逼近上限，把讀取量大的工作派給 sub-agent。
- **任務可以拆開並行**：有 N 個獨立的子任務，例如同時審三個專案，就分派出去。
- **隔離高風險的操作**：破壞性操作要先預演，讓 sub-agent 跑空跑，主 agent 看結果再決定。
- **不想讓探索污染主對話**：探索性的詢問（例如「列出所有可能的假設」）放到 sub-agent，避免噪音灌進主上下文。
- **權限要分開**：碰正式環境的高權限子任務，跟低權限的主對話分開。

### 二、拆多細

- **一次性的 sub-agent**：派一個任務、回一份結果、結束。最常見。
- **長時間執行的工作者**：跨多次迭代，保有自己的上下文。
- **流水線的一站**：上游 agent 的輸出當下游 agent 的輸入，形成一張有向圖。

### 三、上下文的邊界

- **完全隔離**：sub-agent 從零開始讀一份任務說明，看不到主對話。最乾淨，也最浪費 token。
- **父層給摘要**：主 agent 寫一段說明傳給子 agent。中間路線。
- **雙向即時溝通**：子 agent 的進度即時回報給主 agent。彈性高，但上下文很容易爆。

### 四、結果怎麼整合

- **子回報給主，主來拍板**：sub-agent 提出報告，主 agent 整合、決定。
- **子直接寫檔案**：sub-agent 改實際的檔案，主 agent 只看 git diff。
- **投票或合併**：N 個 sub-agent 投票取共識。
- **把推理過程串起來**：把多個 sub-agent 的推理合成一份輸出。

### 五、怎麼交接

- **父到子的單向**：派任務、子完成、結束。最常見。
- **子到父的單向**：子發現問題就中斷，交給父決定。
- **雙向**：子和父反覆對話。這很容易變成一個沒有結構的對話迴圈，是個錯誤做法。
- **有向無環圖**：多個節點照相依關係跑，不循環。適合路徑可以事先決定的流水線。
- **有預算的循環**：圖上允許明確標示出來的回頭邊，例如驗證者把東西打回去重做、重試的邊、或是暫停等人介入的點。

  實際跑在正式環境的 agent 圖通常**不是**無環的。它跟上面那個「沒有結構的對話迴圈」差在兩件事：一是回頭邊要有**約定**，打回去的時候要附上結構化的理由和修正指示，不是自由對話；二是要有**次數上限**，最多打回 N 次，超過就往上交給父層或人。缺任何一件，它就退化成沒有結構的對話迴圈。

### 六、失敗怎麼處理

- **子失敗就整個失敗**：立刻中止。
- **子失敗就重派**：主 agent 換一個 sub-agent 或換一個 prompt 再試。
- **部分成功也合併**：N 個裡面有 M 個成功就可以，把成功的部分合起來。
- **子失敗就記進待辦**：當下不解決，存起來之後 review。

### 七、並行時有一個失敗怎麼辦

- **全有或全無**：任何一個失敗，整批中止。
- **盡力而為**：失敗的跳過，成功的合併。
- **過半數就算數**：N 個裡面 M 個成功就算整體成功。

### 八、留下什麼紀錄

每個 sub-agent 的輸入、輸出、成本、耗時要寫到哪裡？失敗的 sub-agent 的追蹤紀錄要保留多久？

### 九、調度的邏輯寫在程式碼裡，還是交給模型

「該怎麼調度」這件事本身由誰決定？這是一條光譜，不是二選一。

- **全部用腳本調度**：圖的結構寫死在程式碼裡——有哪些節點、什麼順序、怎麼分派和收攏——模型只負責填每個節點的內容。確定性最高、可以重播，適合路徑可以事先決定的任務。
- **腳本搭骨架，模型決定分岔**：骨架寫在程式碼裡，包含階段順序、並行程度、失敗策略；但條件分岔——這個結果該走哪條路、要不要再多開一輪——由模型在節點裡當場判斷。
- **完全交給模型調度**：主 agent 當場決定要開幾個 sub-agent、各派什麼任務。彈性最高，適合開放式的研究，但沒辦法重播，每次跑出來的結構都不一樣。

**選邊的準則：路徑能事先決定就往程式碼那端推，開放式探索就往模型那端推。**

同一套 harness 裡這兩種常常共存：腳本調度的某個節點，內部又是一個模型自主判斷的 agent。

沒做這個決策的症狀有兩種。明明是固定的流水線，卻讓模型每次即興調度，浪費 token 而且結果不穩定。或者明明是開放式研究，卻把流程寫死，圖變成一件緊身衣。

### 十、圖要分兩層看：長期編制和單次任務

把「圖」拆成兩層來看，各自有各自的決策。

**長期的角色編制。** 這是穩定、長壽的角色分工——研究者、驗證者、整合者這些。它跨任務存在，各自的上下文和職責定義要持久化保存。

要決定的是：這份編制存在哪裡（`.claude/agents/`、workflow 的定義檔、還是設計方案）？各角色的記憶要不要跨任務保留？誰有權改動編制（設計者，不是任務進行中的那些 agent）？

**單次任務的結構。** 這是這一次任務的動態結構，會隨著證據進來而開新節點、合併、重排。

要決定的是：**圖跑到一半，結構能不能改？**

- 不能改：結構在開跑前就定死，中途只能中止重來。簡單、可預測。
- 有限度地改：只有預先定義好的變形點可以動，例如「還有新東西就再開一輪」、票數不夠就加派一個驗證者。變形本身也是腳本的一部分。
- 自由地改：模型可以當場增刪節點、重排相依關係。最有彈性，但要配上預算上限，而且變形過程要留下紀錄（對應設計面向 9），否則事後根本重建不出這張圖實際長什麼樣。

兩層沒分開的症狀：把某次任務臨時開的分派當成常設編制固定下來，編制就一直膨脹；或者反過來，每次任務都重新發明同一套角色分工，因為沒有一份長期編制可以召回——這對應設計面向 4 的「計畫存成記憶」。

## 跟其他面向的牽連

- **上下文管理**：sub-agent 是隔離上下文的主要工具。上下文的邊界決定了要不要開。
- **執行迴圈**：每個 sub-agent 自己都有一個執行迴圈。
- **權限與安全**：破壞性的操作先讓 sub-agent 空跑，是常見的做法。
- **Hook**：sub-agent 完成時可以觸發工具執行後的 hook。
- **成效評估**：多 agent 投票本身就是一種每步驗證。
- **可觀測性**：每個 sub-agent 是追蹤紀錄裡的一段。
- **觸發時機**：用定時迴圈觸發一批 sub-agent 分派出去，是常見的組合。

## 在 Claude Code 裡對應什麼

- 內建的 `Agent` 工具，用 `subagent_type` 參數指定要哪一種：general-purpose、Explore、Plan 等等。這是**調度交給模型**的那一端，對應第九項的「完全交給模型調度」。
- `Workflow` 工具，用 JS 腳本把調度結構寫死（`pipeline()`、`parallel()`、`phase()`），模型只填節點內容。這是**調度寫在程式碼**的那一端。它的「跑到沒新東西為止」和預算迴圈，就是第十項講的「有限度地改」的實作。
- 在 `.claude/agents/<名稱>.md` 定義自訂的 sub-agent。這就是第十項講的長期角色編制的存放形式。
- `run_in_background: true` 讓 sub-agent 在背景跑，主對話不會被卡住。
- 並行的做法是在同一次回應裡發出多個 Agent 呼叫，它們會自動並行。

## 常見的錯誤做法

**多 agent 沒解決問題，只是增加延遲。** 這個問題本來照順序就跑得完，硬拆成 sub-agent 反而更慢——傳遞上下文的成本超過了並行省下的時間。

**沒有交接約定的對話迴圈。** 父子之間來回自由對話，沒有明確的終止條件和結果格式。很容易變成死循環。

**回頭邊沒有預算。** 驗證者把東西打回去重做，這在圖上是合法的（見第五項的「有預算的循環」），但如果沒設打回的次數上限，驗證者和執行者就會一直對耗，直到 token 燒完。回頭邊一定要配上次數上限，以及一個往上交出去的出口。

**調度邏輯放錯邊。** 固定的流水線卻讓模型每次即興調度，沒辦法重播又白燒 token；或者開放式的研究卻把結構寫死，圖變成緊身衣。判斷標準見第九項。

**子 agent 又開子 agent，變成失控的樹。** 巢狀沒有上限，token 就失控了。

**沒有幫 sub-agent 分好唯讀和可改動的邊界。** 高權限的子 agent 不該被主 agent 拿去做低風險的探索。

**共用記憶或狀態卻沒有鎖。** N 個 sub-agent 並行寫同一份狀態，就會有競態問題。
