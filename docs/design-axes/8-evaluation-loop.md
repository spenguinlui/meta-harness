# 設計面向 8：成效評估

最容易被忽略，但對「這套系統能不能有系統地改進」影響最大的一條。

它分兩層，性質完全不同。

R-10 是這條面向的最低標準：機器驗得了的產出，交付前必須先自己驗過（見 `universal-care-rules.md`）。R-10 講的是「一定要做」，這個面向講的是「怎麼做」。參考實作在 `experiments/consolidation-loop/`。

## 兩層結構

### 第一層：每步做完就驗

**目的**是模型做完一步立刻驗證，錯了可以馬上修。

**特徵**：在同一個 session 裡發生、自動化、快、便宜。失敗的話把結果回灌給模型，讓它重試或改方向。它屬於執行迴圈的一環。

**例子**：寫完程式碼跑測試、型別檢查、lint；改完 SQL 跑一次執行計畫；動完基礎設施就檢查狀態；呼叫完 API 檢查回應的格式。

### 第二層：跨任務的整體評估

**目的**是衡量整套 harness 的能力。改了 prompt、換了 model、加了 skill 之後，要知道到底是變好還是變壞。

**特徵**：跨 session、跨時間。需要預先建好一組任務，還需要打分機制。用來比較 harness 的不同版本。

**例子**：收集 50 個歷史任務，跑新版 prompt，比較通過率；跑 SWE-bench；收集成功的操作紀錄，換了 model 之後看它還能不能正確規劃。

| | 每步驗 | 整體評估 |
|---|---|---|
| 什麼時候跑 | 任務進行中 | 任務結束後，或在 CI 裡 |
| 對什麼負責 | 這一次的任務 | harness 本身 |
| 失敗之後 | 模型重新規劃 | 工程師重新設計 harness |

沒有第一層，單次任務不可靠。沒有第二層，改 harness 就沒有依據。

## 每步驗的設計

### 一、什麼時候驗

副作用大的動作、可逆性低的動作、後面會依賴的動作。純讀取的不必驗。

### 二、驗到多深

從輕到重：

1. 看工具的回傳值，最便宜。
2. 檢查格式。
3. 語意檢查，這個值合理嗎。
4. 獨立查詢，重新讀一次來對比。
5. 看下游影響，跑測試。

驗證的強度大致等於「出錯之後修復要花多少代價」。

### 三、失敗怎麼處理

重試、重新規劃、停下來問人、或者帶著警告繼續。

預設是停下來問人。自動化程度高的偏向重試或重新規劃。

### 四、由誰來驗

- 規則（lint、格式檢查、測試）：便宜而且確定。
- 讓 LLM 當評審：主觀的任務只能這樣。
- 自己驗自己：便宜，但有偏差。
- 人來驗：高風險的一定要。

有個常見的錯誤是：用同一個 model 自評，然後還大膽相信那個分數。

## 整體評估的設計

### 一、任務集從哪來

- 歷史上成功的案例，確保不會退步。
- 過去失敗的案例，確保不會重犯。
- 刻意設計的挑戰題，涵蓋邊界情況。
- 公開的評測集。

對特定領域的 harness 來說，投報率最高的是「歷史成功」加「過去失敗」的混合。

### 二、規模多大

冒煙測試五到十個，每次 commit 都跑。回歸測試三十到一百個，每晚跑。完整的五百個以上，發版前跑。

少於五個沒有統計意義，超過一百個跑不動。

### 三、怎麼評分

從硬到軟：

1. 完全相符。
2. 比對差異。
3. 行為驗證：產出的東西真的能跑、能通過測試。
4. 評分表：多個維度讓 LLM 評分。
5. 兩兩比較：哪一個比較好。

行為驗證是甜蜜點。它比「完全相符」寬容，又比讓 LLM 評分客觀。

### 四、跟什麼比

跟自己的上一版比（回歸測試，最常用）、跟目前最強的設定比、跟人的表現比。

### 五、失敗要分類

跑完一輪一定要分類，不然「失敗 23%」這個數字沒辦法拿來改進。

- 模型的問題：換 model 或改 prompt。
- harness 的問題：改 harness。
- 環境的問題：修測試環境。
- 規格不清楚：修評測集，或標記成不計分。

## 跟其他面向的牽連

**跟記憶。** 這是整個循環的核心。整體評估失敗就寫進記憶，提醒下次注意。記憶累積之後，靠整體評估來驗證哪些有效、淘汰哪些沒用。沒有評估的記憶就只是一堆噪音。

**跟規劃。** 計畫要先寫好「成功的驗收標準」，那個標準就是每步驗的依據。沒有驗收條件，做完也不知道對不對。

**跟工具執行。** 工具要回傳穩定、可驗證的輸出，評估才寫得出來。工具本身也該標明「怎麼判斷它成功了」。

**跟可觀測性。** 可觀測性給的是追蹤紀錄，也就是「怎麼做的」；評估給的是分數，也就是「做得對不對」。沒有觀測的評估，你只知道失敗了，不知道為什麼。

## 常見的錯誤做法

**只憑感覺。** 沒有評測集，全靠印象。改了東西之後沒辦法回頭比較。

**拿正式任務當評測集。** 會被個案污染。評測集要獨立、穩定、有版本。

**讓同一個 model 自評。** 同一個 model 既做事又評分，分數會虛高。換一個 model 來評，或者改成規則判斷。

**只記分數不分類。** 失敗率 30%，但不知道是哪一類，三個月後還是 30%。

**只做每步驗，不做整體評估。** 以為「每一步都驗過就夠了」，但你不知道整體的勝率。每步驗的是局部，整體評估驗的是全貌。

**整體評估搞太重，結果啟動不了。** 追求一百個完美的案例，結果一個都沒做出來。先做五個粗的，跑起來再慢慢加。

**評估跟正式環境不對齊。** 評估全過了，正式環境還是出包。評測集要從正式環境的實際案例裡抽。

**評測集沒有版本控制。** 改了評測集又改了 harness，分數變化就不知道是誰的功勞。評測集的改動該獨立 commit。
