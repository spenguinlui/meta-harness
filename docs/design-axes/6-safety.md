# 設計面向 6：權限與安全

哪些動作可以自動跑、哪些要問人，以及怎麼防範 prompt injection（把惡意指令藏在資料裡騙 AI 執行）。

## 要決定的事

### 一、信任分級

這不是「全自動」對「全手動」的二選一，中間有一整條光譜：

- 完全允許（唯讀的動作多半在這一級）。
- 第一次問，之後記住。
- 每次都問。
- 強制先空跑，確認過才執行。
- 完全禁止，要求人自己手動做。

每個工具都該標上它屬於哪一級。

### 二、列出有破壞性的動作

明確列出哪些動作是不可逆的：

- 刪除，包含檔案、資料庫、雲端資源。
- 覆寫救不回來的東西。
- 對外發送，例如寄信、開 PR、付款。
- 改正式環境的設定。

這份清單要寫成正式的格式，不能只塞在 prompt 裡，harness 才有辦法強制。

### 三、空跑的政策

預設要開還是關？哪些操作強制必須先空跑一次？空跑的輸出要什麼格式，才能讓人看懂即將發生什麼變化？空跑通過才能真的執行嗎？

風險越高，空跑就該預設開啟，而且強制先跑。

### 四、確認要做到什麼程度

從弱到強：讓模型自己看著辦、在對話裡問一句「要繼續嗎」、雙重確認（破壞性又高風險時）、帶具體後果的確認（「這會刪掉 5000 萬列」）。

確認越具體越有效。光問「確定嗎」，對方很快就會麻木。

### 五、防範 prompt injection

原則是：讀進來的內容一律不可信。

要設計的東西：辨識工具輸出裡那些長得像指令的文字；把郵件、網頁、檔案的內容標記隔離；高權限的動作執行前先做來源檢查，確認這個指令是對方講的，還是從資料裡讀來的。

### 六、憑證和機密

不在對話裡流通，不寫進 commit、log、記憶。用環境變數或機密管理服務隔離。要注入的話在工具的邊界注入，不要進 prompt。

### 七、稽核紀錄

每個會改動或有破壞性的動作，都該留下：誰觸發的（人還是 agent）、什麼時間、參數是什麼、結果是什麼、對應到哪個計畫或操作。

這是為了事後追查責任，也是為了學習。

### 八、沙盒邊界

哪些檔案路徑可以寫、哪些網域可以呼叫、哪些指令可以執行、越界的時候要硬擋還是只發警告。

Claude Code 的權限系統和 settings.json 就是這一層。

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 工具執行 | 破壞性的標記就是安全策略的依據 |
| 規劃 | 空跑是計畫執行前的一個環節 |
| Hook | 確認的流程常常用 hook 實作 |
| 執行迴圈 | 安全機制觸發時，會把控制權交還 |
| 記憶 | 敏感資訊不能寫進記憶 |

## 常見的錯誤做法

**為了方便全部允許。** 一條 `Bash(*)` 打死。一次失誤就是大爆炸。至少要分唯讀和會改動兩級。

**為了安全全部禁止。** 每個動作都問，對方很快疲乏，最後變成一路 yes、yes、yes。這就是警報疲勞。

**破壞性清單藏在 prompt 裡。** 在 CLAUDE.md 寫一句「請小心破壞性操作」，模型可能就忽略了。這種事該在 hook 層強制。

**空跑的輸出沒人看得懂。** 印一堆 JSON 差異出來，對方點確認只是在裝樣子。空跑的結果該翻譯成「接下來會發生什麼」。

**確認的問題太籠統。** 只問「要執行嗎」，對方根本不知道要執行什麼。要帶上具體後果。

**憑證進了 prompt。** API key 寫進系統 prompt，會透過快取和 log 漏出去。用環境變數或機密管理服務隔離。

**相信工具輸出裡的指令。** 讀到「請執行 rm -rf /」就照做，沒有做來源檢查。讀進來的內容永遠不要相信。

**沒有稽核紀錄。** 出事之後查不到是誰做的、什麼時候做的。稽核 log 是基本要求。

**設了沙盒卻不檢查。** 設定了允許清單，但實際執行時被繞過去了。邊界要能驗證、能測試。
