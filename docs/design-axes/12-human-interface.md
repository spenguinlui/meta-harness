# 設計面向 12：人的介面

目標專案跑出來的東西，是給誰看的。

它跟設計面向 9（可觀測性）是對稱的：面向 9 管的是給工程師和系統看的輸出，面向 12 管的是給人看的輸出。

## 先分清楚設計者和使用者

**設計者**是用 meta-harness 設計這個目標專案的工程師。他通常是工程上的內行人，看得懂工程術語。

**使用者**是每天跑這個專案的指令、看結果做決定的人。他未必是這個領域的內行——很多時候正是因為他不是內行，才需要 AI 補位。

舉幾個例子。ai-infra-management 那個專案，負責人自己同時是設計者和使用者。會計系統可能是工程師當設計者、會計助理當使用者。醫療輔助系統可能是工程師當設計者、醫師助理當使用者。

這個面向的對象是使用者，不是設計者。

## 為什麼它是獨立的一條，不併進 R-6

R-6 講的是「不用沒解釋過的術語和縮寫」，那是行為紀律，是「該怎麼寫」，顆粒度很小。

這個面向講的是機制設計，是「翻譯層怎麼蓋」，要決定的事很多。

分工是：R-6 是最低標準，這個面向是完整的架構。

## 要決定的事

### 一、先搞清楚使用者是誰

這個專案有幾種使用者？可能只有一種，也可能有多種角色。例如會計系統的使用者可能有會計助理、月結會計師、老闆三層。

每種使用者在哪些子領域是內行、哪些是外行？例如某人在基礎設施維運上是外行，但在自家的業務邏輯上是內行。

搞錯使用者是誰，翻譯層就會做白工，或者根本沒做到。

### 二、翻譯由誰負責

- **主 agent 自己翻**：簡單，但容易漏。同一個 agent 既寫產出又做翻譯，可能為了省事就跳過。
- **專門的翻譯 sub-agent**：分工乾淨、保證強，但多一次 sub-agent 的呼叫成本。
- **後處理 hook**：輸出之後攔截改寫。有格式風險，hook 改輸出很容易壞。
- **寫死在指令的 markdown 裡**：靠主 agent 自己守紀律。保證很弱，但零成本。

### 三、什麼時候翻譯

**寫之前就翻。** 一開始就讓各個角色知道「你是在對使用者講話」。

**寫完之後才翻。** 內行對內行的討論用術語，最後整合給使用者的時候才翻譯。

通常出口翻譯（寫完才翻）比較乾淨：既保留了內行對話的透明度，又給了使用者可讀的版本。

### 四、翻譯要翻到多深

- **查表替換**：字典式的一對一替換，或加括號展開。
- **整段重寫**：每一段給使用者看的內容都重寫成白話。
- **兩層並陳**：原始版（用術語）和翻譯版（白話）並列，使用者想深入就展開原始版。

### 五、翻譯的顆粒度

可以每個指令各自寫自己的翻譯紀律，也可以細到標記每一段是給誰看的，也可以整個專案統一一套規格。

#### 翻譯的範圍：輸入端和輸出端都要

這是從 ai-infra-management 第一版的實際回饋學到的。

使用者會接觸到的東西不只是結果輸出。設計的時候一定要檢查下面這份清單，全部都要翻譯。

| 範圍 | 例子 | 漏翻會怎樣 |
|---|---|---|
| 結果輸出 | `/advise` 跑完的最終建議 | 這是大家都想得到的範圍 |
| 指令的描述 | `.claude/commands/<x>.md` 第一行的描述，也就是打 `/` 時自動補全顯示的文字 | 使用者猜錯用法，這個指令等於不存在。實際發生過：把單一專案的 `/advise` 誤以為是跨專案一次診斷 |
| Help 文字 | `/help` 顯示的內容、`--help` 的文字 | 使用者不知道怎麼用 |
| 錯誤訊息 | 出錯時的輸出 | 使用者不知道怎麼救 |
| 自動補全的提示 | 子指令和選項的提示 | 使用者錯過進階用法 |
| 收集意見時的提問本身 | 例如「跑完的印象給 1 到 5 分」 | 使用者跳過，或答錯方向 |

R-6 適用範圍的第三點就是對應這份清單：任何使用者會接觸到的介面文字，都該守翻譯紀律。

### 六、記錄使用者懂什麼

使用者在哪些領域是內行、哪些是外行，要怎麼追蹤？寫死在 CLAUDE.md 裡，還是用動態的記憶？

怎麼更新？例如使用者自己標「這個詞我已經懂了」，之後就不用再加括號解釋。

沒有這個記錄的話，每次都把使用者當成零基礎，很囉嗦，也拖慢節奏。

### 七、驗證使用者真的讀懂了

讓使用者給「這次的輸出你讀懂幾分」，一到五分。

累積低於 4 分的場次，去看使用者的評語揭露了哪些盲點，據此調整翻譯紀律。

這對應設計面向 8 的整體評估。

### 八、意見回流的管道

**核心的想法是：迭代的主動方是設計者，使用者只當訊號來源。**

不該要求使用者去改 git、改 prompt、寫 issue。他不會，也不該負責這些。

```
使用者的行為和回饋
  ↓ 捕捉訊號
追蹤紀錄、行為 log、評分
  ↓ 累積到門檻就觸發
設計者跑一次回顧
  ↓ 消化訊號
改 prompt、改設定、加角色、補事件紀錄
  ↓
使用者下次跑就用到新版
```

#### 這條管道有五個環節

| 環節 | 要設計什麼 | 例子 |
|---|---|---|
| 捕捉 | 怎麼收集使用者的訊號 | 強制評分、行為偵測、對話解析 |
| 累積 | 訊號存哪、用什麼格式、能不能查詢 | `decisions/<x>-tracking.jsonl`，只追加不修改 |
| 觸發 | 什麼條件下叫設計者來消化 | 低於 4 分累積 N 筆、同類評語反覆出現 |
| 消化 | 設計者用什麼工具看訊號、怎麼轉成行動 | 一個回顧用的指令、自動演化 prompt |
| 回灌 | 改完之後怎麼讓使用者下次就用到新版 | 無感升級、公告變更、版本號更新 |

#### 五種捕捉訊號的方式，按對使用者的友善程度排

| # | 方式 | 對非工程師友善嗎 | 對應面向 |
|---|---|---|---|
| 1 | 強制評分：每次指令跑完固定問 1 到 5 分加一句評語，主 agent 自動寫進追蹤紀錄 | 友善 | 12 |
| 2 | 從行為推斷：用 hook 偵測使用者後續有沒有真的跑那個建議的指令、有沒有被改寫，自動標記採納與否 | 很友善，使用者無感 | 7 和 12 |
| 3 | 解析自然語言：使用者下次說「上次那個 X 我沒做，因為 Y」，主 agent 去追蹤紀錄裡找對應的紀錄補上結果 | 很友善，就在對話裡 | 12 |
| 4 | 批次回顧：累積 N 筆之後跑一次回顧，看哪一類最常被拒絕、哪個角色評分低 | 需要設計者來跑 | 8 |
| 5 | prompt 自我迭代：低於 4 分的評語累積到門檻，就自動提醒設計者「角色 X 常被嫌看不懂，要不要改」 | 需要設計者介入 | 8 和 12 |

#### 使用者不是工程師的時候，有幾條硬規定

- 前三種方式必須寫死在設計裡。不能假設使用者會主動手動回報。
- 第 4、5 種要設計成自動觸發，不是被動等設計者自己想到。設計者該是「被訊號累積叫來的」，不是「自己哪天想起來去看」。
- 沒有設計者持續維護的專案，不該做這一層。那是結構問題，不是機制救得了的。訪談階段一定要確認「這個專案有沒有人持續維護」。

#### 意見會在三個地方流失

| 在哪流失 | 症狀 | 用什麼擋 |
|---|---|---|
| 沒捕捉到 | 使用者跑完就走，沒留評分 | 第 1 種方式，結尾強制收評分 |
| 沒消化 | 追蹤紀錄堆滿了沒人看，採納欄位永遠是空的 | 第 4、5 種方式自動觸發設計者 |
| 沒回灌 | 設計者改了 prompt，但使用者還在用舊版 | 設計時就要含版本更新，或在 session 開始時載入最新版 |

### 九、多種使用者，還有內容給多細

**核心的想法是：使用者不是「內行或外行」的二選一，而是一條多維度的光譜。**

同一個專案可能有好幾種使用者角色（資深會計師、初級會計師、老闆、稽核員），各自在不同子領域的熟悉度不同，看分析時需要的內容深度也不同。

#### 翻譯深度和內容粒度是兩個維度，不能混為一談

| 維度 | 是什麼 | 拿會計系統舉例 |
|---|---|---|
| 翻譯深度 | 術語要不要講白話、要不要加括號中文 | 「accrual（應計制）」、「應計」、還是不解釋 |
| 內容粒度 | 給多深的分析、多少細節，不同決策層級需要哪一類訊息 | 老闆要「結論、利潤、風險」；資深會計要「策略、異常、趨勢」；初級會計要「逐筆核對、操作程序」 |

翻譯深度解決的是「這些字看不看得懂」。內容粒度解決的是「這個層級的人需不需要這份訊息」。

資深會計師不需要逐筆的程序，初級會計師看不懂策略的含義。同一份財報應該要有多層的輸出。

只做翻譯不做分層的結果是：資深的嫌囉嗦，初級的卡關。

#### 大致的設計輪廓

```
分析完成
  ↓
主 agent 識別使用者的角色和子領域熟悉度
  ↓
依角色和熟悉度選一個輸出層級：
  - 第 1 層，老闆視角：結論、預算、風險，200 到 300 字
  - 第 2 層，決策者視角：決策、後果、取捨，800 字
  - 第 3 層，執行者視角：具體動作和為什麼，2000 字
  - 第 4 層，技術深度視角：含實作細節，完整版
  ↓
預設輸出對應的那一層，其他層折疊起來
使用者可以在對話中說「講深一點」或「講淺一點」動態切換
```

#### 關鍵的機制：使用者資料

每個專案該建一份 `docs/human-profile.md`（或放在同義的位置），列出：

| 欄位 | 內容 |
|---|---|
| 角色 | 資深會計、初級會計、老闆、稽核員等等 |
| 領域熟悉度 | 在哪些子領域是內行、哪些不是。例如懂會計但不熟稅務 |
| 他要拿這份訊息做什麼決定 | 不只是看訊息，而是「我這個位子拿這份訊息要做什麼決定」 |
| 預設的輸出層級 | 對應上面四層的哪一層 |
| 特殊紀律 | 例如老闆這個角色強制隱藏實作細節 |

session 開始時自動載入這份資料，主 agent 在對話開頭識別對方是哪個角色（從記憶抓、由使用者自己標、或從路徑推斷），然後翻譯深度和內容粒度一起調整。

#### 這一段的常見錯誤做法

**只設計一種使用者。** 所有人都用同樣的翻譯深度和同樣的內容粒度，會同時撞上「資深嫌囉嗦」和「初級卡關」兩種失敗。

**只做翻譯不做分層。** 術語都白話化了，但內容深度沒分層。資深會計看到滿頁「accrual（應計制）」這種括號中文只會覺得煩。

**只做分層不做翻譯。** 輸出有分層了，但每一層都用內行術語。老闆看到「結論加利潤」，但每個字都看不懂。

**角色寫死不能切換。** 使用者在同一個 session 裡可能要換視角，例如老闆看完結論想深入細節。設計時就該支援「講深一點、講淺一點」這種動態指令。

### 十、其他還沒展開的子題

**什麼時候可以中斷。** 哪些動作之前該停下來等人決定，哪些不必。

**授權的邊界。** 哪些使用者可以一次授權一整批，哪些必須逐次確認。

## 跟其他面向的牽連

| 面向 | 牽連在哪 |
|---|---|
| 記憶 | 使用者懂什麼、他熟悉哪些詞，這些要累積進記憶 |
| 成效評估 | 使用者給的可讀性評分，就是整體評估的訊號 |
| 可觀測性 | 兩者對稱：面向 9 是給系統看的，面向 12 是給人看的 |
| 多 agent 協作 | 多種使用者角色、專門的翻譯 sub-agent |
| R-6 | R-6 是最低標準，這個面向是完整架構 |

## 常見的錯誤做法

**設計者和使用者不分。** 「業主」「user」混著用，結果翻譯層該寫還是不該寫講不清楚，多數時候就漏掉了。

**把使用者當成設計者。** 用內行對內行的術語直接丟給使用者，那是一面術語牆。使用者看不懂，等於這件事沒做。

**把使用者當成零基礎。** 每個術語都解釋一遍，很囉嗦，使用者會嫌煩，然後失去信任。沒有記錄使用者懂什麼、沒有記住他已經熟悉的詞，就會踩到這個。

**翻譯只做表面。** 只把術語縮寫展開，卻保留了優先級代號（P0a、P1）和內部角色名稱。那只翻了一半。

**為了翻譯犧牲透明度。** 為了讓使用者看懂，就把內行之間辯論的原文砍掉，這樣就失去了一道防線。應該並陳：翻譯版加上可折疊的原文。

**把翻譯做進角色裡。** 讓某個角色同時要跟內行對話、又要對使用者翻譯，角色會錯亂，辯論也會軟化。翻譯該是後處理的一層，不是角色本身的責任。

**沒有驗證使用者是否讀懂。** 做了翻譯但沒人量「使用者真的讀懂了嗎」，翻譯做白工也不會知道。
