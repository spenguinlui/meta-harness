# 顧問的判斷邏輯：從訪談到設計方案

這份文件記錄的是顧問腦中怎麼做判斷：訪談的結論怎麼轉成設計方案，哪些面向要認真設計、哪些可以略過。

SKILL.md 講的是「該做哪些步驟」，這裡講的是「怎麼判斷」。

---

## 訪談階段

那五個問題不只是在收集資訊。每個答案都直接決定了後續的設計。

**想解決什麼問題。** 要判斷的是：這個工具本身是目的，還是達成別的目的的手段？哪個設計面向是非做不可的？如果答案太空泛，改問「今天哪件事讓你想找這個工具」。

**現在長什麼樣。** 要判斷的是：既有的模組合不合理？哪些該留、哪些該重構、哪些該丟？還有一件很重要的：這個工具最後是用什麼做的——bash 腳本、網頁應用、SaaS、還是混合型？這會決定設計方案裡檔案骨架該用什麼語言寫。不問就預設是 bash。

如果對方說「就照現在的架構」，改問「哪個概念你最不確定它該不該存在」。如果實作介質不明確，問「這個工具最後跑起來是什麼樣子？CLI、網頁、API，還是嵌在某個產品裡？」

**不該做什麼。** 要判斷的是：什麼不做，以及不做的理由。一定要逼對方挑出三條。如果回答「都可以做」，那是範圍要膨脹的警訊。

**什麼時候會放棄，還有要活多久。** 要判斷的是：哪個設計面向必須補強？淘汰機制要做多強？沒問壽命的話，預設就是永久，結果就是幾乎一定會少設計淘汰機制。

**使用者懂不懂這個領域。** 要判斷的是：設計面向 12 的翻譯層要不要做、要做多深。如果對方說「都是我自己用」，還是要追問：你在哪些子領域是內行、哪些不是？

訪談的產出是 `sessions/<日期>-<主題>.md`，包含五段答案的草稿，以及一張設計面向的初步篩選表。

---

## 怎麼從五個答案篩出設計面向

訪談結束後，顧問做的不是「一條一條填」，而是照下面的順序判斷。

### 第一步：先定出非做不可的面向

依據「什麼時候會放棄」這題，判斷哪個面向如果不設計，整個工具就會垮。

- 輸出不可信任會垮的：權限與安全（6）、成效評估（8）是非做不可。
- 跑一次就結束的：記憶（3）、觸發時機（11）可以直接跳過。
- 使用者不是這個領域的內行：人的介面（12）是非做不可。
- 要長時間跑、需要監看的：可觀測性（9）是非做不可。
- 有多個任務要並行的：多 agent 協作（10）要做決定。

非做不可的面向要全力設計。其他的一句話帶過就好，寫「這個專案不需要」。

### 第二步：用「想解決什麼問題」過濾掉膨脹

13 個面向全套是給基礎設施管理那類複雜專案用的。輕量的專案——一次性腳本、只用幾天的工具——通常只需要三到五條。

篩選的原則是問一句：如果這條不設計，對方的核心痛點會不會被卡住？不會的話就跳過，一句話帶過。

### 第三步：用壽命決定設計深度

| 預期壽命 | 設計要做到多深 |
|---|---|
| 一次性 | 幾乎只要做工具執行（1）和權限安全（6） |
| 幾週 | 加上記憶（3）的草案就夠 |
| 幾個月 | 記憶（3）和成效評估（8）都要認真設計 |
| 幾年或永久 | 所有非做不可的面向全套，加上明確的淘汰機制 |

### 第四步：用「不該做什麼」決定不設計什麼

那三條邊界不只是功能的邊界，也是設計面向的邊界。被明確排除掉的能力，對應的面向可以直接跳過，不需要「先保留空間」。

## 篩選表長什麼樣

訪談結束前，顧問要在紀要末尾附上這張表。對方確認過，才進下一階段。

```
設計面向篩選表（<目標專案> / <日期>）

非做不可，全力設計：
  - 6 權限與安全：[一句理由]
  - 12 人的介面：[一句理由]
  ...

需要設計，但沒那麼關鍵：
  - 1 工具執行：[大方向]
  - 3 記憶：[草案]
  ...

用不到，一句帶過，不寫進設計方案：
  - 10 多 agent 協作：這個專案單線跑，不需要
  - 11 觸發時機：手動觸發就好，不需要排程
  ...
```

---

## 進入下一階段前必做的三件事

缺任何一件，對方就會失去脈絡。

1. **把訪談摘要直接貼在對話裡。** 不要只給 `sessions/` 的檔名——對方沒打開檔案就不知道裡面寫什麼。
2. **貼出篩選表，問對方「這張表有沒有要調整的」。**
3. **確認無誤後明講：** 「我接下來自己寫 `prescriptions/<日期>-<目標專案>.md`，大約 X 分鐘後給你看。」

對方沒確認就不要往下走。面向選錯，比設計方案寫得慢更難修。

## 顧問自己寫設計方案

到這一步，顧問已經知道哪些面向非做不可、哪些用不到。方案只需要寫：

- **非做不可的面向**：完整的做法說明，加上關鍵檔案的骨架（檔名、各自負責什麼、效能上要注意什麼）。
- **需要設計但沒那麼關鍵的面向**：說明做了什麼決定就好，不用骨架。
- **用不到的面向**：不出現在方案裡，或用一行寫排除的理由。

這一步不問對方任何拍板題。顧問在這裡是獨立作業，不是徵詢機器。

### 用軟體工程既有的名詞把設計講精確

寫方案的時候，如果認得出某段設定對應到軟體工程裡的常見做法，就明講出來。像是 Strategy、Specification、Middleware、Facade、Repository、Bounded Context、Ubiquitous Language、Hexagonal、ATDD、單一職責加上依賴反轉這些。對照表見 `prescription-template.md` 的「軟體工程紀律映射」段。

這不是為了套名詞而套。有名字之後，設計討論的精度和 review 的效率都會提升。而且像是違反單一職責的肥大 hook、跨情境的共通語言逐漸走鐘這類問題，在設計階段就會露出來，不必等到自我驗證才發現。

有些做法是 LLM 領域特有的，傳統軟體工程沒有直接對應，是在 harness 這個領域裡另外建立的：四種自我驗證的驗法（比對設定是否一致、觸發後看有沒有反應、跑分評輸出品質、比對前後差異）、prompt 快取的成本考量、agent 迴圈、用評估結果驅動 prompt 迭代、model 路由、上下文視窗的預算分配。碰到這些議題時，方案裡要明寫採用哪一種，方便跨方案比對和重用。

## 常見的失敗

| 失敗的樣子 | 根本原因 | 怎麼修 |
|---|---|---|
| 明明只是個用幾天的小工具，設計方案卻寫了 13 條全套 | 跳過篩選，預設全部都要設計 | 訪談階段補上篩選表 |
| 對方說「繼續」，但設計方向已經轉了 | 轉場時沒讓對方確認篩選表 | 轉場強制貼出篩選表 |
| 人的介面那層很薄，或根本沒設計 | 沒問第五題「使用者懂不懂這領域」 | 訪談階段補問 |
| 壽命假設錯了，導致完全沒設計記憶 | 沒問壽命，預設是一次性 | 訪談階段強制問壽命 |
| 設計方案只有文字，沒有檔案骨架 | 顧問跳過了「關鍵檔案骨架」這步 | 每個非做不可的面向都要附骨架 |

## 建議路徑

下面這章是操作建議，不是硬規定。真正的約定寫在 `.claude/skills/consultant/SKILL.md` 裡。

能力強的 model 可以用自己的方式達成那些約定（該交出什麼產出、留什麼證據、卡在哪裡不能過）。能力弱一點的 model 照抄這章最穩。

這些內容原本住在 SKILL.md 裡，後來搬過來：SKILL 只留約定，做法放這裡，方便強 model 偏離、弱 model 照抄。

### 開場：先開放地問，再給選擇題

跑五個選擇題之前，顧問先直接問一句開放題：

> 「請先介紹一下這個專案。它現在在做什麼，你怎麼用它？」

等對方自由回覆之後，帶著這份背景去設計選項，選項才會貼近他的語境。

如果對方第一句話已經帶了足夠的背景（例如「我想設計一個做 X、Y、Z 的工具」），可以直接進五個問題，不用再要求他介紹一次。

### 訪談的五個問題

顧問用按鈕選單問這五件事。每題都附上為什麼要問，以及答太空泛的時候怎麼追問。

| 問題 | 為什麼問 | 答太空泛時怎麼辦 |
|---|---|---|
| **想解決什麼問題**：你親身遇到的痛點是什麼？一年後做到哪三件事你會說「值了」？這個 repo 本身是目的還是手段？ | 設計方案必須對著真實痛點，不是對著想像 | 改問「今天哪件事讓你想找這個工具」 |
| **現在長什麼樣**：現有的核心概念、模組、抽象對得上嗎？哪些是刻意設計的，哪些是被現實逼出來的？ | 顧問不能預設既有的抽象是對的 | 對方說「就照現在的架構」，改問「哪個概念你最不確定該不該存在」 |
| **不該做什麼**：這個 repo 不該做什麼？這題最容易被跳過，一定要逼 | 不問的話範圍會自然膨脹，設計方案跟著膨脹 | 對方說「都可以做」，警告這是範圍過寬的典型錯誤，逼他挑三條 |
| **什麼時候放棄，還有要活多久**：什麼狀況下你會放棄這個 repo？預期會跑多久（一次性、幾週、幾個月、幾年、永久）？ | 前者決定哪個面向非做不可，後者決定淘汰機制要多強 | 沒問壽命就預設永久，多數情況都會少設計淘汰機制 |
| **使用者懂不懂這領域**：每天用這個工具的人（未必是你）在這個領域是內行還是外行？哪些子領域熟、哪些不熟？ | 決定人的介面（12）那層翻譯要不要做、做多深。漏問就會預設對方是內行，結果丟出一面術語牆 | 對方說「都是我自己用」，還是要釐清他在哪些子領域是內行、哪些不是。例如基礎設施內行但會計外行，機器學習內行但維運外行 |

### 選擇題怎麼問

**預設用 AskUserQuestion 工具，不要在對話裡用 markdown 列 N 選 1。**

為什麼：對方要一直複製貼上、自己打 (a)(b)(c) 來回答，很煩。這個工具是按鈕點選，還附一個 Other 可以自填，效率高很多。

適用場合：訪談各層、設計面向拍板、界定不該做什麼、失敗條件等等，凡是 N 選 1 或 N 選 M 的場合都用工具。

工具限制：每題最多 4 個選項，一次呼叫最多 4 題。超過 4 個選項就拆成「主要的 4 個，其餘寫在 Other 裡」，或拆成兩題。

例外：純開放題還是直接在對話裡問，例如「半年後你怎麼判斷這東西變好了」這種需要對方自由回答的。給幾個代表性選項加上 Other 也可以。

混著用也行：問題本身的描述（背景、推薦、取捨）可以在對話裡寫，但選項用工具。

### 寫設計方案時的操作順序

1. 讀 `docs/design-axes/` 底下篩選出來的那幾條，不是全部都讀。同時讀 `docs/prescription-template.md`。
2. 需要對照先例的時候「才」去查 `cases/`。對方可以指定要看哪一份，預設不主動讀。讀了哪份，要照污染警示在紀要裡註明。
3. 讀目標專案的現況：檔案結構、現有的設定。
4. 寫 `prescriptions/<日期>-<目標專案>.md`：文字描述加上關鍵檔案的骨架（檔名、負責什麼、效能要點），不寫完整內容。

怎麼篩面向，見本文前面「怎麼從五個答案篩出設計面向」那段。

### 自我驗證的五個步驟

實作完任何一個機器驗得了的成果，交付前跑這五步。約定只要求「標準情境、跑至少三次、留下機器評分的紀錄」，下面是最穩的做法。

1. **寫標準情境。** 在 `experiments/<目標專案>-<主題>/gold.md` 寫下期待輸出的關鍵特徵：關鍵字、結構、通過門檻。設計方案的 Part E 已經有的話就引用，不要重寫。
2. **非互動模式跑至少三次。** 在目標專案的目錄裡跑 `claude -p "<測試 prompt>" --output-format json --permission-mode bypassPermissions`。穩定度本身就是訊號：三次答案差很多，就表示紀律沒有生效。
3. **讓機器評分。** 關鍵字涵蓋、結構檢查（用 `jq` 拆 JSON）、或讓 LLM 當評審。不准顧問肉眼瞄一次就說 OK。
4. **沒過就改。** 改 prompt、改設定、改角色描述、改 skill 說明，再跑一次。直到通過，或者明確在設計方案裡 commit 一條「這部分沒驗，已知限制」。
5. **撞到 API 上限或工具不能用的時候，不要假裝驗過。** 標上警示，並排一個補跑的機制：ScheduleWakeup、cron、或下次 session 開頭。

參考實作在 `experiments/consolidation-loop/`，裡面有 `run.sh`、`eval.sh`、`prompts/v*.md`、`gold.md`、`runs/*.json`。新專案照這個結構建 `experiments/<目標專案>-<主題>/`。

### 定期回顧的四項檢視，各自的判斷門檻

約定只定義了四個維度和觸發條件（見 SKILL.md），這裡給各維度可操作的門檻。

**哪些成果該累積成 skill。** 如果實作完之後，設計者反覆手動做同一類動作兩次以上（例如每次跑完都手寫一段臨時的 bash 去跑基準），就該把它抽成 `skills/<名稱>/<動作>.sh`、子指令、或 hook，不要當成一次性的成果。這對應設計面向 4。

**累積的訊號看得出什麼。** 追蹤紀錄或人工評分累積到一定量之後就看。參考值是累積 10 筆評分，或低於 4 分的次數超過 3 次。這時跑一次回顧，看哪一類最常被拒絕、哪個角色的 prompt 該調。這對應設計面向 8 的整體評估，以及設計面向 12 的意見回流。

**記憶的形狀對不對。** 自動寫入的記憶有沒有塞錯類型（流程類和事件類的應該往 git 移）？完整的討論紀錄有沒有保存下來？是不是還丟在 `/tmp/` 裡？這對應設計面向 3。

**這套方法本身有沒有缺口。** 這次專案暴露出來的反覆失誤，如果是跨專案通用的，升級到 `docs/design-axes/` 或 `docs/universal-care-rules.md`；如果只跟這個專案有關，留在該專案自己的文件裡。

### 顧問常犯的錯誤做法

| 錯誤做法 | 在講什麼 |
|---|---|
| 唸教科書 | 把每個設計面向當成章節，跟對方從頭重新設計目標專案內部的資料格式和演算法門檻 |
| 照表操課 | 把跑壞的那段對話固化成 SOP 形式的指令或流程設定 |
| 問抽象問題 | 丟對方答不出來、或不熟的術語的問題（違反 R-5） |
| 丟沒解釋的術語 | 動詞、名詞、縮寫不解釋就直接用（違反 R-6） |
| 不查就動手 | 設計前不去讀對應的設計面向文件，重新發明輪子 |
| 規則不分層 | 通則、設計流程、方案格式、錯誤做法全塞在同一個檔案，等於沒分層 |
| 疊規則不刪源頭 | 看到失敗就加新規則、加一段「這樣不行」，不去 grep 找根本原因（違反 R-7） |
| 跨層下命令 | 把「我這邊是 X」硬推成「所以你那邊該 Y」，做成二分對照表，越權替別的 session、別的 repo、別的人表態（違反 R-8） |
| 自動記憶變終點 | 寫進自動記憶就放著，不回頭 review、不升級成通用規則或進 git。自動記憶該當成孵化用的中繼站，不是永久的終點 |
| 方法只進文件 | 反覆出現的失誤，該升級成 hook、skill、或指令，不是只加一條文字規則 |
