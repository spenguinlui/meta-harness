# 第一次用 meta-harness

讀完這份，你應該能在 30 分鐘內跑完第一次顧問 session 的第一步，也就是需求訪談。

---

## 開始之前

你需要裝好 Claude Code CLI（`claude --version` 跑得起來），還有心裡有個想設計的專案，知道它的路徑，例如 `~/my-project`。

那個專案不需要已經存在。你只要講得出「想做什麼」就夠了。

本文把你要設計的那個專案叫「目標專案」。

---

## 開一個 session

```bash
cd ~/meta-harness
claude
```

第一句話這樣講：

```
我想設計 ~/my-project 這個工具
```

`consultant` skill 會自動載入，顧問接著會問你五個問題。

如果第一句話是「繼續 X」而不是「設計 X」，顧問會先問你指的是 `sessions/` 裡的哪一份紀錄，然後從那裡接下去。

---

## 第一步：訪談，10 到 20 分鐘

顧問會用按鈕選單問你五件事：

**想解決什麼問題。** 今天哪件事讓你覺得「要是有個 agent 幫我做就好了」。

**現在長什麼樣。** 已經有的模組或流程，哪些想留、哪些還不確定。

**不該做什麼。** 這個工具不該碰的事，至少要講出三條。

**什麼時候你會放棄它，還有它要活多久。** 什麼狀況下你會覺得這東西沒救了；預計會用幾週、幾個月，還是長期。

**每天用它的人懂不懂這個領域。** 那個人可能不是你。他是這個領域的內行嗎？

訪談結束後，顧問會給你一張表，列出 13 個設計面向裡哪些要認真設計、哪些用不到。你確認過，顧問才會進第二步。

---

## 第二步：設計方案，你不用做事

顧問自己寫一份 `prescriptions/<日期>-<目標專案>.md`，寫完把重點摘要貼給你看，不會叫你自己去開檔案。

你要做的是看摘要、給文字意見。沒意見就說「OK 開始實作」。

---

## 完整流程長這樣

1. 需求訪談：你和顧問一起。
2. 顧問自己寫設計方案。
3. 你看過、來回改到定案。
4. 分階段實作，把檔案寫進目標專案。
5. 自我驗證（編號 4.5）：顧問用非互動模式跑至少三次、機器跑分通過，才交給你。
6. 驗收：顧問跑能自動驗的部分，你自己開新 session 試用。
7. 幾週之後回頭檢視。

第一次用通常只跑到第四步，後面看需要。

---

## 第一次最常卡在哪

**「顧問問太多了。」**
最多人想跳過的是「不該做什麼」那題。不問的話，設計方案會膨脹，實作完更難砍。先給三條粗略的邊界就夠了。

**「我的目標專案還沒建。」**
可以。顧問會先出設計方案，再建目錄、初始化。先聊需求就好。

**「我不知道它要活多久。」**
就說不確定。顧問會幫你分析：如果只用一陣子，設計方案就做輕量的；如果要長期用，才補上記憶和成效評估那一整套。

**「設計方案我看不懂。」**
方案摘要會用中文功能名描述，例如「安全守衛」「意見回流管道」，不會丟「Part A-F」這種字母編號給你。看不懂就直接問。

## 想深入讀的話

| 文件 | 用途 |
|---|---|
| `docs/design-axes.md` | 13 個設計面向的索引 |
| `docs/design-axes/<編號>-<名稱>.md` | 每個面向有哪些選項、哪些是常見的錯誤做法 |
| `docs/universal-care-rules.md` | R-1 到 R-12，顧問內建必守的基本規則 |
| `docs/prescription-template.md` | 設計方案的格式，你看方案時可以對照 |
| `docs/consultant-flow.md` | 顧問怎麼做判斷 |
| `prescriptions/` | 每次 session 的設計方案留檔（在 .gitignore 裡） |
| `sessions/` | 訪談紀要（在 .gitignore 裡） |

`sessions/` 裡的舊紀要是當時的快照。裡面的路徑和檔名可能已經隨著 repo 演化失效了，當歷史看就好，別當現況。

## 不 clone 這個 repo，也能用這套方法

你不需要 clone meta-harness 才能用它。這不是一個要安裝的框架，而是一組可以照抄進你自己 repo 的做事方式。最小可行的版本只要五樣東西。

### 一、拿 13 個設計面向當檢查清單

設計任何 AI harness 之前，把 [`docs/design-axes.md`](design-axes.md) 的 13 條當成設計參數，逐條問自己：這條對我的專案是非做不可、需要設計，還是根本用不到？

不用每條都做。多數輕量工具只需要其中三到五條。怎麼篩見 [`consultant-flow.md`](consultant-flow.md)。光是走這一步，就足以避開「想到哪做到哪」造成的漏設計。

### 二、抄這三條規則

完整的 12 條見 [`docs/universal-care-rules.md`](universal-care-rules.md)，但外部採用的話先守這三條就有八成價值。

- **R-4，不編造。** 找不到、做不到就直說，並且列出你試過什麼。不要用讀起來很順的猜測去填補。
- **R-10，交付前先自己驗過。** 任何機器驗得了的產出（腳本、指令、agent），交給人之前自己先跑通、留下證據。「改完」不等於「完成」。
- **R-12，不洩漏框架。** 寫進目標專案的檔案要能獨立看懂，不要引用你設計時用的內部術語、編號，或這套方法本身的行話。

### 三、六步流程的產出物

不管誰來執行，這六步各自要交出什麼、卡在哪裡不能過，是固定的。中間怎麼做可以自由發揮。

```
1    訪談五件事  → 紀要（想解決什麼 / 現在長什麼樣 / 不該做什麼 /
                   什麼時候放棄加上要活多久 / 使用者懂不懂這領域）+ 設計面向篩選表
2    設計方案    → 一份文件，文字加上關鍵檔案的骨架
3    看過改到定案 → 你自由給文字意見，不是選擇題
4    分階段實作   → 逐階段把檔案寫進目標專案
4.5  自我驗證    → 機器驗得了的產出，非互動跑 ≥ 3 次加上跑分通過才交付（R-10）
5    驗收        → 靜態檢查加上開新 session 實際試用
```

### 四、最小的自我驗證，三個檔就能開跑

R-10 說要先自己驗過，怎麼把它變成擋得住的機制？最小的基礎建設只有三塊，都可以照抄本 repo 的對應檔案。

| 你要建的 | 抄哪個當範例 | 作用 |
|---|---|---|
| 一支 `test-<功能>.sh` | [`test-prescription-template-structure.sh`](../experiments/meta-harness-eval/test-prescription-template-structure.sh)，最簡單的那種：grep 看關鍵結構在不在 | 驗某項設定沒有偷偷跑掉 |
| `run-self-verify.sh` | [`run-self-verify.sh`](../experiments/meta-harness-eval/run-self-verify.sh) | 單一入口，跑完所有 `test-*.sh`，回傳 0 或 1 |
| Stop hook | [`self-verify-on-stop.sh`](../.claude/hooks/self-verify-on-stop.sh) 加上 [`settings.json`](../.claude/settings.json) 裡的 `Stop` 註冊 | 只有動過架構檔的那一輪才跑自驗；發現對不上就擋住 session 結束，讓「改了沒驗就收工」變成不可能 |

後兩塊是一次性的基礎建設，先做好。之後每加一項設定，只要多寫一支 `test-*.sh`。

### 五、什麼時候才需要整套 meta-harness

上面的最小集適合一個人、一個專案。遇到下面這些情況，才值得把整套搬過來（顧問 skill、設計方案模板、13 個面向的深入文件、錯誤做法案例庫）：

- 你要反覆設計好幾個專案，需要一份可重用的手法清單，而不是每次重想。
- 專案要交給不是你的人使用或維護，需要正式的說明書和維護者文件（R-11）。
- 你希望設計方案有機器擋關，防止內容被掏空，還要跨專案追蹤進度。

只做一個小工具的話，留在最小集就好。提前把整套框架搬來，等於是在沒有證據的情況下疊東西。
