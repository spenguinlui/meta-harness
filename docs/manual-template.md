# 說明書的格式

驗收通過之後，交付給目標專案的說明書該長什麼樣。

跟設計方案的差別：方案是給設計者看的設計文件，說明書是給每天用這個工具的人、以及日後接手維護的人看的。

說明書由 `/document` skill 從設計方案、專案現況、以及使用者的背景資料自動產出，可以重跑刷新。

---

## 兩種讀者，要寫成兩份文件

這對應設計面向 9 和 12 的分野，不可以混在一起。

**給使用者的說明書**，讀者是每天用這個工具的人，未必是設計者。用他的語言寫，以任務為導向。落在 `README.md` 和 `docs/<主題>.md`。

**給維護者的文件**，讀者是日後接手改、接手擴充的工程師。講技術、講架構、講為什麼這樣設計。落在 `CONTRIBUTING.md` 或 `docs/architecture.md`。

混在一份的結果是：設計者嫌囉嗦，使用者看不懂。

**對外公開的網站也要拆兩頁。** 同樣是這個分流，只是換到對外的場合：

- `docs/index.html`（或等價的入口）是使用者版，語言深度比照使用者說明書。
- `docs/maintainer.html`（或等價）是維護者版，語言深度比照 CONTRIBUTING。
- 兩個入口頁互相連結，並明講「你現在看的是哪一版、另一版在這裡」。

把兩種讀者塞進同一個公開頁面，就只是把同樣的錯誤換個場地重犯一次。

## Viewer 說明書結構

以 `README.md` 當入口，比較深的內容往 `docs/` 下沉。

每一段都要標來源，也就是這段內容是從哪裡萃取的。寫不出來源就是在編造，違反 R-4。

| # | 段落 | 內容 | 來源 |
|---|---|---|---|
| 1 | 這是什麼、能做什麼 | 一段話定位，加上能力條列 | 設計方案 Part A |
| 2 | 快速開始 | 需要先裝什麼、怎麼安裝、第一次怎麼跑。走最短路徑到「看到它動起來」 | repo 現況，例如 package.json 的 scripts、既有的 README |
| 3 | 存取與參數 | `.env` 需要哪些值，以及怎麼拿到（帳號、token、權限怎麼申請） | `.env.example` 加上 Part A |
| 4 | 怎麼用、常見任務 | 「我想做 X，就這樣下指令」的具體範例。這是使用者最常讀的一段 | Part A 加上 Part E 的使用者意圖 |
| 5 | 工作流程迴圈：人和 AI 怎麼分工（條件性） | 畫出 AI 自動循環的迴圈，以及人在哪裡交出去、什麼時候拿回控制來驗收。ASCII 圖最清楚。這跟第 4 段不同：第 4 段講「能叫它做什麼」，第 5 段講「叫了之後 AI 自己在迴圈裡做什麼、你什麼時候不用管」 | 專案有 AI 自動迴圈時必寫。對應設計面向 5 和 12 |
| 6 | 有哪些指令和 skill | 有哪些指令、各自什麼時候用（一句白話）。每個指令要列齊所有的叫法——去讀指令檔的內文，不要只抄開頭的描述，否則使用者會以為只能用嚴格的語法。互動式的詢問要獨立一段呈現：會跳出什麼問題、選項有哪些、想跳過該帶哪個參數 | `.claude/skills/` 和 `.claude/commands/`，逐個指令讀內文 |
| 7 | 會產出什麼、怎麼確認做對了 | 會生出哪些檔案和結果，使用者怎麼驗證成功了 | Part D 的產出加上 Part E 的驗收 |
| 8 | 不做什麼、已知限制 | 明確排除的能力，加上已知的限制。防止誤用和錯誤期待 | Part A 的「不該做什麼」加上 Part F |
| 9 | 出錯怎麼辦 | 常見的失敗怎麼救，附上錯誤訊息對照 | Part F 加上實際踩過的坑 |
| 10 | 誰維護、怎麼回報 | 維護的人是誰，怎麼回報問題和給意見 | 訪談時的設計者資訊，加上設計面向 12 的意見回流管道 |
| 11 | 詞彙表（條件性） | 領域術語的白話對照 | 只有在使用者不是這個領域的內行時才寫。對應設計面向 12 的翻譯層 |

**精簡版**（壽命短、或純自用的工具）：至少要有第 1、2、3、4、8 段。

**有 AI 自動迴圈的專案**：第 5 段必寫。使用者最容易卡在「我交了任務，AI 到底在自動做什麼、我什麼時候該介入」。沒有這段，他就只看到一張任務表，不懂流程。

## 維護者文件結構

放在 `CONTRIBUTING.md` 或 `docs/architecture.md`。

| 段落 | 內容 |
|---|---|
| 架構概覽 | 主要模組、資料怎麼流、關鍵的抽象。一張圖或一段話講清楚骨架 |
| 各元件怎麼串起來 | hook、skill、指令、設定各自做什麼、彼此怎麼接 |
| 怎麼擴充 | 加一個新元件、新指令、新規則，各要做哪些步驟 |
| 為什麼這樣設計 | 連回設計方案，或摘要關鍵決策加上刻意排除的範圍 |
| 怎麼驗證改動 | 該跑哪些測試、怎麼跑自我驗證，連回 Part E |

## 雙語慣例

- **寫成兩個檔案，不要交錯排。** 交錯排的話兩種語言都讀不順。
- **一個主檔加一個對應檔。** 主檔用專案的工作語言，看既有的 README 和 CLAUDE.md 是什麼語言就跟著。
  - 主檔是中文：`README.md` 中文，`README.en.md` 英文。
  - 主檔是英文：`README.md` 英文，`README.zh-TW.md` 中文。
  - docs 和 CONTRIBUTING 同樣規則：`<名稱>.md` 加上 `<名稱>.en.md` 或 `.zh-TW.md`。
- **每個檔案第一行放語言切換行**，例如 `> 🌐 **繁體中文** | [English](README.en.md)`。
- **兩版同一次生成**，由同一份萃取出來的事實去渲染。結構、錨點、章節順序完全一致，這樣才不會慢慢走鐘。
- **不翻譯的東西**：程式碼、檔案路徑、指令、環境變數名、識別字、表格裡的值（例如顏色碼、px、node id）。只翻散文和表格標題。

## 深度要跟著讀者調整

第 4 段和第 10 段的深度，由「使用者是不是這個領域的內行」決定。判斷依據是訪談的第五題，或 `docs/human-profile.md`。

| 使用者類型 | 術語怎麼處理 | 內容給多細 |
|---|---|---|
| 這個領域的內行（例如前端工具給前端工程師） | 術語直接用，不加括號 | 可以給實作細節 |
| 外行（例如基礎設施工具給會計） | 術語講白話，加括號展開 | 給結論和怎麼做，藏起實作細節 |
| 多種角色都會看 | 分層輸出，老闆視角和執行者視角折疊起來 | 每個角色預設展開一層 |

只調翻譯不調粒度的話，資深的人嫌囉嗦、初學的人卡關。

**自創詞和業界術語要分開看，校準的維度不一樣。**

業界術語（staging、dry-run、hook、CI、regression、fan-out 這類）套用上面的表：內行直接用，外行講白話加括號。

自創詞和專案內部的分類（專案自己創的詞，像是「內視 / 外視」「Stage X」「G-N / R-N」這種），不分內行外行，第一次出現一定要白話註解，或直接改用功能名稱。

內行也不該被迫去學你內部的分類詞。他懂的是業界通用的詞，不是你公司專案裡創的名字。

## 進階：大型專案的文件怎麼組織

這節是選用的，來源是 ai-infra-management。

當專案累積了很多份文件（超出基本 README 那 1 到 10 段，而且有多個記憶或文件的落點），光把文件平鋪出來，使用者會不知道從哪讀起。有兩個做法可以讓厚重的文件仍然好導航。

**一、給一個分層的閱讀順序。** 不要平鋪，而是給階梯：五分鐘進入狀況、三十分鐘理解架構、動手前或動正式環境前必讀、領域知識（碰到再查）、演化與歷史。放在 `docs/_READING_ORDER.md`，README 指向它。

這對應設計面向 12，也是設計面向 3 那個「把記憶當文件平鋪丟出去讓人自己猜」錯誤做法的反面。

**二、給一張「想寫東西該放哪」的路由表。** 當專案有多個記憶落點（例如知識、決策、操作手冊、事後檢討），給一張決策表：「想寫 X 就該進哪一格」。避免內容亂放，之後要召回時全變成噪音。放在文件分流的判準檔裡，例如 `docs/<knowledge>/_README.md`。

**什麼時候用。** 專案文件超過大約八到十份，或者有多種記憶落點的時候。

小專案（figma2code 那個規模）不必。平鋪那 1 到 10 段就夠了，硬搞一個五層階梯反而過度。這對應篩選設計面向時的原則：壽命和規模決定深度。

## 產出守則

1. **每段都要有來源。** 寫不出來源就表示那段在編造（R-4）。改標 `[需負責人補：<什麼>]`，不要用流暢的文字虛構。
2. **可以重跑，但不要盲目覆蓋。** 重跑的時候如果專案已經有手寫的內容，要保留或合併，不要直接蓋掉。偵測到大量人工編輯的痕跡就先問一下。
3. **反映已經驗證過的狀態。** 說明書是驗收之後才產出的，要寫這個專案現在真的會做什麼，不是設計時想像它會做什麼。
4. **指令和路徑要跟 repo 的實際情況對得上。** 列出來的指令、腳本、檔名都要真的存在。產出前 grep 對一遍。
